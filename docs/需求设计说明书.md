## 1. 范围与目的

### 1.1 本文件是什么

- **需求基线**:每条功能需求有编号(`FR-*`)与**验收标准**;实现完成与否按本文件判定。
- **实现期唯一入口**:新会话要动代码,先读本文件,再回设计稿查数值推导。

**不是什么**:① 不重述设计稿的玩法规格与数值表(那在 §5–§19);② 不写实现细节(文件 / 类 / 函数结构),那属于变更归档与资源规范。

### 1.2 首发范围

| | 内容 |
|---|---|
| **In** | **P1 全量**(见 §10):6 场域 × 36 地块、十阶段解锁、园丁等级、播种 / 浇水 / 晒太阳 / 施肥 / 收获、仓库入仓、每日计数快照 + 日志保留期清理;模式边界层(P1 必须定死,§23);客户端为 **Cocos web-mobile** 构建,承载于 ihomy 内嵌 |
| **In(视 ihomy 侧进度)** | **积分闸门**(园币 → 积分单向兑换)。依赖 ihomy 仓三个前置动作(新 feature code / `familyId` 归位 / 家庭级开关,设计稿 §30.4),**属 ihomy 仓事项**,本仓不代做 |
| **Out(首发不做)** | P2–P5 的玩法(季节矩阵数值层 / 变体系统 / 市集 / 间作连作 / 天气事件 / 设施 / 工具 / 烹饪 / buff / 图鉴套装 / 节气事件 / 周挑战 / 扦插杂交 / 专精分工 / 成就 / 拍照晒图 / 引导);**P6 全部**(单人 Solo / 多人 P2P / standalone provider / `/worlds` 存档管理页);**Steam 与 native 构建**;两个候选(年度回顾 / op-log 结算网关) |

> 首发不含 Solo/P2P ⇒ 首发**不需要客户端侧权威**,世界权威在服务器(§3)。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| **核心 `garden-core`** | 无 IO 的纯函数包:成长 / 季节 / 营养 / roll / 全部判定。**同一份代码**服务所有端 |
| **世界 World** | 一份存档的容器(地块 / 仓库 / 钱包 / 工具 / buff / 挂单 / 图鉴 / 快照 / 日志 / 成员 / 设置)。**泛化了「家庭」**:`kind = FAMILY / COOP / SOLO` |
| **成员 Member** | 世界内的玩家身份 `player_uid`(ULID,`CHAR(26)`),跨端稳定 |
| **场域 Venue** | 可种植的空间:窗台 / 大盆 / 生态缸 / 后院 / 农场 / 大棚。**列名与 code 一律 `venue`,不是 `field`** |
| **地块 Plot** | 场域内的网格单元,共 **36 块**;`(family_id, venue, slot_no)` 唯一 |
| **权威 Authority** | 有权判定「这次动作成不成立」的那一端:`LOCAL` / `HOST` / `SERVER`。**三者互斥** |
| **op-log** | 追加型操作流水,`op_id` 全局唯一,是幂等与重放的依据 |
| **`content_version`** | `content/*.json` 的 sha256;配置漂移的拦截依据 |

> ⚠ `world_id` ≠ 账号。ihomy 登录态只是「服务器模式取世界」的一个来源,不是世界的定义。

### 1.4 技术口径

**已定**:

| 项 | 结论 |
|---|---|
| 客户端 | **Cocos Creator 3.8**,首发 **web-mobile** 构建;native 构建不在首发 |
| native 绑定 | **Cocos 原生插件调用核心**(不经 `napi`,也不引 C++)。首发不用,仅登记口径 |
| Web 绑定 | `wasm-bindgen` |
| Steamworks | **由 Cocos 侧承担**(Steam SDK 走 Cocos 原生插件),核心侧不写 Steam API |
| 存档 | **`GardenSave v1`**(唯一格式;`save_version` = `1.0`) |
| 服务端 | **Java 21 + Spring Boot 3.5 + MyBatis-Plus + MySQL 8 + Redis 8**(与 ihomy 同栈),ihomy / standalone 两个 provider **同栈** |
| 版本号 | 对外首发版本 **`1.0.0`**;开发期内部版本号按 2026-10-13 指示**不再迭代**(`VERSION` 维持 `V0.4`) |

**⚠ 未定**:核心的实现语言(设计稿 §32 说 Rust,§28.1/§28.5 说 Java jar,两者互斥)。**这是 P1 的第一个阻塞项,见 §9 首条**。已定的只是它的**接入方式**(native 走 Cocos 原生插件、Web 走 `wasm-bindgen`),语言本身待裁。

## 2. 角色与权限

| 角色 | 是谁 | 能力 |
|---|---|---|
| **OWNER(家长)** | ihomy 家庭 owner | 全部玩家能力 + 花园设置(时间比例 / 每日积分上限 / 积分闸门开关)+ 导入导出世界 + 删除世界 |
| **MEMBER(成员)** | ihomy 家庭成员 | 全部种植 / 照料 / 收获 / 仓库 / 市集能力 |
| 未登录 | — | 仅 `GET /garden/meta`(能力协商,免登录) |

- 权限沿用 ihomy「**登录即可 + 家庭隔离**」,**不新增 `sys_auth` 权限码**。
- ⚠ **专精(后续期)不绑 `sys_user_role`**——那是权限体系,「只有 OWNER 能烹饪」是错的。
- 跨家庭访问一律 `404`(不泄露存在性)。

## 3. 运行模式与首发取舍

设计稿 §24 定义三种模式:单人 Solo(本地权威)/ 多人 P2P(房主权威 + op-log)/ 服务器(服务端权威)。**首发只跑服务器模式的一种:`platform=IHOMY`。**

| 端 | 权威 | 首发 | 说明 |
|---|---|---|---|
| `SERVER` + `platform=IHOMY` | 服务端 | ✅ 唯一 | 承载于 ihomy;`garden_world.id = family_id`(恒等映射) |
| `SERVER` + `platform=STANDALONE` | 服务端 | ❌ | 同栈自建服务器,不在首发 |
| `HOST`(P2P) | 房主 | ❌ | P6 |
| `LOCAL`(Solo) | 本机 | ❌ | P6 |

三条硬规定(不因首发收窄而放松):

1. **积分只在 `platform=IHOMY` 产出**;其余模式 UI 必须明示「不可兑换」。
2. **权威不可并存**:一个世界同一时刻只有一个权威;换模式 = 显式迁移,不是双向同步。
3. **核心必须确定性**:三端重放同一 op-log 必须得到逐字节相同的状态哈希。

> ⚠ 首发虽不实现 Solo/P2P,但 **P1 必须把边界层定死**(`GardenPort` + `GardenPlatform` 抽象、`garden-core` 零平台依赖、`GardenSave v1`、`op_id` 幂等)。**这些后加等于重写**(设计稿 §21/§23)。

## 4. 功能需求(FR)

> 标注 `[P1]` = 首发;`[P2]` 起 = 首发不做,为后续期登记。每条给「需求 → 验收标准」。

### 4.1 场域与地块 `[P1]`

- **FR-01 场域与网格**:六场域 `WINDOWSILL / PLANTER / TERRARIUM / BACKYARD / FARM / GREENHOUSE`,合计 **36 块**地,网格规格由 `content/venues.json` 推导(`slot_no` → `(row, col)`),**不加列**。土壤 `POT / BOX / FIELD / TANK` 与场域绑定(仅空地时可改)。
  *验收*:六场域背景各自渲染正确;每场地块数与设计稿一致(窗台 3 / 大盆 3 / 花箱 3 / 缸 2 / 后院 6 / 深井 2 / 农场 8 / 经济垄 2 / 大棚 6 …合计 36);跨场域 `slot_no` 不串号。
- **FR-02 十阶段解锁**:作物阶段按 `content/unlock.json` 的**进度阈值**解锁(**走进度不走等级**)。
  *验收*:进度达阈值即解锁下一阶段;解锁消耗园币(200/400/800/1500/3000);阈值改动只改 JSON,不动代码。
- **FR-03 地块唯一性**:`(family_id, venue, slot_no)` 唯一,播种落在此键上。
  *验收*:重复播种同一地块返回 `409`,不产生第二行。

### 4.2 播种 `[P1]`

- **FR-04 播种**:`POST /garden/plot`,入参 `{venue, slotNo, cropCode}`。校验:场域已解锁 → 等级满足 → 土壤偏好匹配 → 园币充足。
  *验收*:① 条件 UPDATE `WHERE crop_code IS NULL`,影响 0 行即 `409`(不靠「先查后写」);② 扣园币与落 `garden_plot` 同事务;③ 响应回传本次 `variant`(若该期已有变体系统)。
- **FR-05 相邻效应冻结**:伴生 / 化感 / 遮荫在**播种时结算并冻结**(不做移栽)。
  *验收*:播种后移动 / 改变邻居不影响已结算结果;单块地相邻加成合计钳制在 `[−20%, +15%]`。
- **FR-06 重茬判定**:按 `plot.prev_family` 判定同科连作,惩罚 `1.0 / 0.85 / 0.70 / 0.55`,`**只作用于成长**`;播种非同科即清零。
  *验收*:连续同科第 4 茬成长系数为 0.55;`prev_family` 为空或不同科时系数为 1.0。

### 4.3 照料 `[P1]`

- **FR-07 浇水 / 晒太阳**:各 `POST /garden/plot/{id}/water|sun`,**按地块**冷却 `720 分钟`(12h),基础加成 `120 分钟`。
  *验收*:冷却内重复返回 `409` 且**带剩余秒数**(前端据此倒计时);条件 UPDATE,0 行即失败。
- **FR-08 施肥**:`POST .../fertilize`,扣 `15 园币`,冷却 `720 分钟`,加成 `360 分钟`。
  *验收*:园币不足返回 `1008` 且**带差额**;扣款与写 `last_fertilized_at` 同事务。
- **FR-09 每地块每日只计首次照料经验**:`LEVEL_XP_CARE = 5`,每地块每日只计 1 次。
  *验收*:同日对同一地块第 2 次浇水不增经验;跨日恢复。
- **FR-10 状态异常(纯函数推导,无状态位)**:`待补水 / 干旱 / 霜冻 / 徒长 / 灼叶 / 沤根 / 虫害 / 锦化`。缺水提示 48h、枯萎冻结 72h;`锦化`是唯一正向状态(×1.15 成长 / +20% 产量,72h 或异常即失效)。
  *验收*:⚠ **植物永不死亡**——不存在任何「归零 / 铲除」路径;状态全部可逆。
- **FR-11 生态缸补水 / 大棚通风**:`mist` 冷却 `168h`(7 天,仅缸内地块);`ventilate` 冷却 `24h`(夏季高温必需)。
  *验收*:非缸内地块调 `mist` 返回 `400`;冷却策略同 FR-07。

### 4.4 收获与仓库 `[P1]`

- **FR-12 收获入仓**:`POST /garden/plot/{id}/harvest`。条件 UPDATE 锁定地块 `WHERE crop_code = ? AND growth >= total`,`INSERT` 仓库行——**同一事务**。
  *验收*:未成熟 `409`(带「还要长 X」);仓库满 `409`(带引导文案);重复提交由 `op_id` 幂等兜底,不重复入仓。
- **FR-13 仓库同码堆叠**:`garden_inventory` 按 `(family_id, item_code)` 唯一,`qty = 0` 即删行。
  *验收*:收获同码果实数量累加;`qty` 归零后行消失。
- **FR-14 收获清空照料加成**:`care_boost_minutes` 收获时归零;`harvest_count` 递增。
  *验收*:收获后该地块加成不再计入成长。
- **FR-15 园币入账**:收获按参考价计园币入**个人钱包**(`family_id + player_uid`),仓库共享 / 钱包独立。
  *验收*:A 收获的园币只进 A 的钱包;B 的余额不变。

### 4.5 等级与图鉴 `[P1]`

- **FR-16 园丁等级**:`1 + floor(sqrt(total / 12))`,**封顶 100**。经验来源:照料 5/次/地块/日、收获按作物阶段 `15/25/40/60/90/120`、新作物首收 `30`(每种一次)。
  *验收*:Lv100 对应 ≈123,750 进度点;等级不超 100;新作物首收只计一次。
- **FR-17 十个里程碑**:Lv10/20/…/100,每 10 级改一条规则(设计稿 §4.2)。
  *验收*:到达里程碑时对应规则生效且仅生效一次。
- **FR-18 图鉴独立表**:`garden_codex(family_id, crop_code)`,**永不删除**;加成 `+0.5%/种,硬顶 +33%`。
  *验收*:日志清理后图鉴不归零;加成达到 33% 后不再增长。

### 4.6 成长与数值 `[P1]`

- **FR-19 成长公式**:所有乘子相乘,**总乘数硬顶 ×3.0**;核心禁止浮点比较(一律整数基点)。
  *验收*:乘子叠加超 3.0 时按 3.0 计;同一输入两次计算结果完全一致。
- **FR-20 季节纯函数**:`3-5 春 / 6-8 夏 / 9-11 秋 / 12-2 冬`;室内软化 `×0.5`、缸内 `×0.7`;大棚季节免疫。
  *验收*:同月同场域结果恒定;大棚内热带作物全年可种。
- **FR-21 气温双轨**:霜冻用**实测气温**(阈值 0℃),**不用日历**;成长用**当日预报 `tempMin/tempMax` 均值**,日内外恒定(避免进度倒退)。
  *验收*:天气数据缺失时**不报错**,按季节默认均温继续算,页面天气位显示「暂无」。
- **FR-22 营养模型**:`NUTRIENT_MAX/FLOOR/BASELINE/DECAY_HOURS = 100/20/50/72`。
  *验收*:营养不低于 20;衰减周期 72h。

### 4.7 经济与积分闸门 `[P2 数值层 / 视 ihomy 侧进度]`

- **FR-23 园币**:唯一园内货币,个人钱包;收支见设计稿 §12.1。**积分 → 园币不通**。
  *验收*:不存在任何积分换园币的接口或路径。
- **FR-24 积分闸门(单向)**:园币 → 积分,**仅 `platform=IHOMY`**。事务 + `coins >= N` 条件扣,`PointsService` 写流水与扣币同事务,**每日上限判定先做**。
  *验收*:并发下不超发;**必须带 `familyId`**;家长可整关此功能。
- **FR-25 市集**:成员挂单 + 系统收购保底 + 系统代售。**挂单价 ≤ 系统参考价 × 3**;挂单 48h 自动下架。
  *验收*:家人交易与系统收购同价(无套利);超上限价被拒。

### 4.8 设置 `[P2]`

- **FR-26 家长设置页(仅 OWNER)**:读写 `garden_world.settings` 的 `time_ratio` / `daily_points_cap`。
  *验收*:非 OWNER 调用返回 `403`;⚠ **不得**回落到 `sys_parameter`(全局表 + 值上限 500 字符)。

### 4.9 后续期功能(登记,首发不做)

| 10 | `garden_log` | 成长日志(行为流水,**保留 180 天后物理删**) | 世界 |
| 11 | `garden_world` | **世界注册表**(标识 / 来源 / 权威 / 世界级设置) | 世界 |

- **表数口径**:本仓建在独立 `games` 库,**不动 ihomy 的 81 张表**(§16.5/§23 的「表数 → 92」是 ihomy 侧集成事项,本仓不涉及)。
- 十一张表**都不加 `deleted` 软删**(游戏数据,误删可重种;加软删只会让每个查询多一个恒定条件)。唯一例外是**世界级删除**,见 §9。

### 5.2 结构变更双文件

- **`schema.sql`(全量)+ `migrations.sql`(幂等增量),两处必须同步**;空库全量导入实测。
- ⚠ **首发前置工作**:这两个文件**目前尚不存在**,需按 §5.1 建立。
- 配置**不进库**:`content/*.json` 由 git 管,不写种子段,内容变更不需要迁移。

### 5.3 标识层口径(硬规定)

- `user_id` 这个列名在花园表里**彻底消失**;六处改 `player_uid CHAR(26)`,另有 `seller_uid` / `created_by` 同改。
- **`sys_user_id`(ihomy 绑定列)只加在 `garden_member`**;任何新增表都不得再引入 `user_id` 列。
- `player_uid` 与 `sys_user_id` **单向绑定、永不互相覆盖**。
- `garden_log` 补 `op_id CHAR(26)` 唯一 + `lamport` + `device_id` + `origin`。
- **旁注(未决)**:设计稿 §34.2 另提 `garden_member.steam_id` / `steam_guard_verified`,与「绑定列只在 `garden_member` 加一个」的纪律需要一次口径统一,见 §9。

### 5.4 存档 `GardenSave v1`

```json
{ "save_version": "1.0",
  "content_version": "<sha256(sorted content/*.json)>",
  "world": { "world_id": "01J...", "kind": "FAMILY", "origin": "IHOMY",
             "authority": "SERVER", "external_ref": "ihomy:family:123", "host_epoch": 0 },
  "exported_at": "...", "exported_from": "SERVER", "checksum": "<sha256(payload)>",
  "payload": { "plots": [], "inventory": [], "wallet": [], "tools": [], "buffs": [] } }
```

- **两道闸门**:`save_version` 管结构(不同则走代码迁移),`content_version` 管数值解释(不同则走 `content/migrations/*.json` 数据迁移)。**两道都对才导入**,否则输出差异清单并拒绝——**不猜、不半读取**。
- **统一为 v1**:设计稿 §31.2/§33 原有的 `GardenSave v2` 提法**作废**,一律 `v1`。
- 迁移信任分级:`S→C 新世界`可认领(时间戳必须净化)、`S→C 已有世界`**禁止回灌**、`P→C` 只走 op-log 重放。
- **配置唯一真相源**:仓库根 `content/`;**Cocos 侧副本由构建前拷贝脚本同步**(不手工维护两份)。

### 5.5 日志容量与保留 `[P1]`

- `garden_log` 保留 **180 天**,超期物理删;**单家庭上限 5000 行**(超出优先删最旧的照料类行,保留收获行)。
- **删除必须走自定义 XML 分批 `DELETE ... LIMIT`**(项目规则:物理删走自定义 SQL),定时任务 `@Scheduled(cron = "0 30 3 * * ?")` 与回收站同批。
- ⚠ **`garden_stat` 快照 + `garden_codex` 图鉴 + 日志清理三者必须同批上线**——只清 log 会让人物等级与图鉴归零。

## 6. 接口需求

### 6.1 端点(`/api/garden`,登录 + 家庭隔离)

**首发必做 `[P1]`**:`GET /garden`(全景)、`POST /garden/plot`(播种)、`POST /garden/plot/{id}/water|sun|fertilize|harvest`、`POST /garden/venue/{venue}`(解锁场域)、`GET /garden/meta`(能力协商)。

**后续 `[P2+]`**:`mist` / `ventilate` / `warehouse/sell|fridge|eat` / `recipe/{code}` / `tool/{code}/upgrade` / `plot/{id}/facility` / `listing`(GET·POST·buy) / `settings/*`(time-ratio·points-cap·ai-suggest) / `export`·`import` / `rtc/signal`(P2P) / `WS /ws/garden` / `settle`(候选未排期)。

- 所有写接口 `@OperationLog`;同码仓库扣减用条件 UPDATE 原子防超扣。
- ⚠ **所有写接口额外接受 `Idempotency-Key` 头(值 = `op_id`)**,由 `garden_log.op_id` 唯一索引兜底。

### 6.2 错误码与幂等

- **复用现有 `ResultCode`,不新增枚举**:`OK=0` / `BAD_REQUEST` / `NOT_FOUND` / `FORBIDDEN` / `INSUFFICIENT_POINTS=1008`。
- 关键约定:`园币不足 → 1008 且带差额`;`冷却中 / 未成熟 / 仓库已满 → 409 且带剩余量`;`非解锁或跨家庭地块 → 404`;`阶段等级不足 → 403 且差几级`;`天气缺失 → 200 不报错`;`场域非对应土壤 → 400`。
- **统一原则:所有扣减都是条件 UPDATE + 0 行即失败**,不用「先 select 再 update」。
- 幂等动作清单:照料类(条件 UPDATE)、收获(条件 UPDATE + 同事务入仓)、卖出/成交(条件扣减 + 同事务)、兑换积分(事务 + 每日上限先判)、播种(条件 UPDATE)、**任意写动作(重试/重放/重连走 `op_id`)**。

### 6.3 能力协商 `GET /garden/meta`(三端统一入口,可免登录)

返回 `protocol_version` / `platform` / `content_version` / `world` / `capabilities`。**客户端按 `capabilities` 渲染**;**能力缺失时不渲染入口(而不是置灰)**。

## 9. 未决项

**⚠ 最优先,阻塞 P1:核心跑在哪个语言里(设计稿内部自相矛盾)**

设计稿对「核心」给了**两个互相排斥的答案**,而首发恰好落在矛盾点上:

- §32 说核心是 **Rust**(`garden-core`,Web 走 `wasm-bindgen`)。
- §28.1/§28.5 说两个 provider **共用 Java 同栈**,`garden-core` 作为**无依赖纯函数模块(jar)被两个 provider 引用**;§30.1 的 `GardenPlatform` 接口签名也是 **Java**。

而首发是 **`platform=IHOMY` 的服务器权威模式**(§3):判定全部在服务端,首发**不需要客户端侧核心**(Solo / P2P 才需要,那是 P6)。于是首发的核心**天然落在 Java 服务端**——Rust 在首发链路里可能是零参与。

三个选项(必须选一个,否则 P1 会在「写哪份核心」上卡住):

| 选项 | 含义 | 代价 |
|---|---|---|
| **A. 核心用 Java(首发最省)** | 权威核心在服务端,Java 一份;客户端只做呈现与提交意图 | Rust 退到 P6 才需要;届时要第二份实现 → 正是 §28.5 想避免的「另一套实现的漂移」 |
| **B. 核心用 Rust,Java 侧经 JNI 调用** | 单一实现,三端一致;服务端为每个部署平台产一份 native 库 | 服务端构建 / 打包复杂度上升;首发就吃这份复杂度 |
| **C. 两份实现 + golden 一致性测试** | Rust(客户端)/ Java(服务端)各写一份,靠 op-log 重放断言状态哈希一致 | 每条规则改两遍;测试成为唯一护栏 |

> 判据在 §1.4 与 §24.1:**核心必须「同一份代码、同一份配置」**,否则三端一致(golden 重放)只是纸面保证。若选 A 或 C,§28.5 的「jar 被两个 provider 共用」提法要保留,而 §32 的 Rust 决定要重述为「仅客户端侧」。
> **未定之前不要动 `garden-core` 的语言选型**;`garden-core/` 现有的 Rust 代码是上一轮脚手架的产物,不是已定口径。
