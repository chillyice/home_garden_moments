## 1. 设计原则（合并 V1 + 新增）

1. **推导不落库**：阶段、营养、成长进度、园丁等级、图鉴全部是「当前时刻」的纯函数，读取时实时计算。改公式 / 阈值无需数据迁移，历史植物自动按新规则解释——后期改动便宜的第一道保险（沿用 V1）。
2. **数值外置集中**：魔法数字收在 `PlantConst`（后端）与作物 / 食谱**仓库配置**（内容型数值），改平衡不动业务代码（V2 起内容型数值下沉到 `content/*.json`，不进库，见 §16）。
3. **配置驱动品种**：V1 的「品种只决定视觉」升级为「品种数值全部配置化」——一行 `content/crops.json` 记录决定季节矩阵 / 土壤偏好 / 时长 / 产量 / 价签，新增作物零代码。
4. **渐进解锁**：十个阶段 + 一条回填阶梯（§3）交叉解锁「一块新地方 / 一批新作物 / 一个新机制」。**Lv1 就给满 8 种**（窗台 + 花箱 + 缸三块地）。**等级与解锁解耦**（V2 最重要的一次纠错，详见 §4.1）：等级（Lv1–Lv100）只管展示与里程碑，内容解锁走**独立的进度阈值表**，避免 sqrt 曲线让玩家一周打通全部十个阶段。
5. **事件驱动、日志只追加**：一切动作只写 `garden_log`（action 扩展），不修改历史；等级 / 图鉴 / 食谱解锁均从日志 + 仓库推导，不另存状态。
6. **币种隔离 + 单一受控出口**：园内一切收支走**园币**（个人钱包），与 ihomy 积分彻底分开；积分只能经市集按固定汇率 + 双重日封顶**单向**兑现，`积分 → 园币` 不通。不新造多套货币，但经营货币与内容创作货币必须隔离——否则农场会刷爆积分，毁掉「写内容换积分」的激励与积分商城定价基础。天气走 `WeatherService`、通知走 `NotificationService`、食材入冰箱复用厨房 `family_item`，仍不新造背包 / 烹饪引擎。
7. **一处收口**：所有倍率在**一个纯函数**里相乘（见 §10），带**总乘数硬顶 ×3.0**——经济与平衡只有一处可调、一处可封顶。
8. **总量与结构分离**：时间比例 R（§12.3）缩放全局产出**总量**，作物间相对价值完全不变；结构（谁比谁划算）由季节 / 土壤 / 工具 / 阶位决定。两个维度互不干扰，家长调 R 不会破坏平衡。
9. **世界可移动、权威唯一**（§24）：存档形态与运行位置解耦——同一份 `GardenSave` 可在单人 / P2P / 服务器三种模式下运行；但任一时刻只有一个权威，换模式 = 迁移 + 换权威，**不做双向同步**。
10. **可信产出只在可信端**（§24 / §29）：积分与跨模块出口只认服务器权威；本地与 P2P 的产出是「本地账」，UI 必须明示——把原则 6 的「币种隔离」扩展到「模式隔离」。
11. **核心确定性**（§1 / §25）：`garden-core` 内**禁 `Math.random`、禁直接取 `now()`、禁浮点比较**（一律整数基点），时间与天气由调用方注入。这不是洁癖，是 P2P 重放与结算校验成立的前提。

## 2. 核心玩法循环

```
解锁阶段(等级+园币) → 开垦地块 → 播种(买种) → 日常照料(浇水/晒太阳/施肥/生态缸补水)
        ▲                                                          │
        │                        季节 × 土壤 × 天气 × 气温 × 事件 × 工具 × buff
        │                                                          ▼
   园丁升级 ← 图鉴收集 ← 收获入【家庭仓库】 ←──────────────── 成熟结果
                                         │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              市集(挂单/售系统)    入厨(冰箱食材)        加工(材料/强化)
                    │                   │                   │
                    │                   └── 食谱烹饪 → 短效 buff ──┘
                    │
                    └── 园币 --[10:1 + 日封顶]--> 积分（单向，家长可关）
```

- 家庭**共用一片农场**：仓库、工具、buff、等级均为家庭级；**园币是个人钱包**（各管各的账）；照料动作按**地块**冷却，任一成员都能操作。
- 收益来自**错季 / 错土壤的对比**：当季作物 + 匹配土壤 + 高阶工具同时叠加才能拿到高倍率，这是「不只种一种」的机制保证（不是靠提示文案）。

## 3. 场域阶梯：十一个阶段交叉解锁

> 用户诉求原文：「从室内花盆到花箱到生态缸，室内到后院到农场，需要有个渐进过程」+「后期到了大棚或者养殖基地就尝试种植热带或者其他地方的植物」+「解锁增加一些大花盆的同时解锁作物」「解锁农田设施和作物」「解锁更多家庭后院农田作物」。

**核心决策一：场域与作物交叉解锁**，每阶段同时给「一块新地方（或一处扩建）」+「一批新作物」，玩家一直在有新东西种。

**核心决策二：室内线走完再出户外**（窗台 → 大花盆 → 花箱 → 缸 → 后院 → 农场 → 大棚）。玩家不会「出去到后院又被拉回室内」，进度有清晰的「从家到田」叙事。

**核心决策三：难度按「可见性」分层，不按时间硬塞**（见 §5.7）。

| 新序 | 阶段 | 解锁 | 地块 | 累计 | 作物 | 进度门槛 | 新机制 | 该阶段的调子 |
|---|---|---|---|---|---|---|---|---|
| **1** | 室内窗台 | 新场域 | 3 小盆 | 3 | **8 种** | 0（初始） | 基础照料循环 | 全是最好养的，**教玩家种** |
| **2** | 窗台扩建 · 大花盆 | 附属 | +3 大盆 | 6 | **6 种** | 200 | 深根空间 | 室内扩容，专攻香草与观赏 |
| **3** | 花箱 | 新场域 | +3 格 | 9 | **6 种** | 600 | 混种邻作 + **锦化**（正向挑战首现） | 花箱能混种，开始看组合 |
| **4** | 后院 | 新场域 | +6 块地 | 15 | **10 种** | 1500 | **天气事件 + 同科重茬**（可见难度） | 第一次有地有土，第一次怕天气 |
| **5** | 后院深土区 | 附属 | +2 深土垄 | 17 | **6 种** | 2800 | **遮荫 + 虫害 + 化感压制**（可见难度） | 地块变深变少，木本与香草园娇气 |
| **6** | 生态缸 | 新场域 | +2 缸 | 19 | **10 种** | 4800 | **每周补水维护 + 隐性难度首登场** | 有维护成本的温室，难养作物集中在此 |
| **7** | 农场 | 新场域 | +8 垄 | 27 | **12 种** | 9000 | **整行灾害 + 规模管理**（规模风险） | 全部是容易种的基础作物，先把地铺满 |
| **8** | 农田设施 | 附属 | +2 经济垄 | 29 | **8 种** | 14000 | **设施维护 + 授粉管理**（经济机制） | 有设施才种得了经济作物 |
| **9** | 后院 / 农田扩充 | 附属 | +1 垄 | 30 | **6 种** | 20000 | **多产地分散种植**（产能管理） | 回头填满前面场景，开始讲究搭配 |
| **10** | **温室大棚** | 新场域 | +6 垄 | **36** | **12 种** | 34000 | **温度管理 + 季节免疫**（终极风险画像） | 热带 / 外来植物，不怕季节但怕温度 |
| **11+** | 前面场景的高级作物 | 回填 | — | — | 见 §5.2 | 50000 起 | — | 回到旧场景挖深度，直至 200 种 |

- 合计 **36 块地**（窗台 3+3、花箱 3、缸 2、后院 6+2、农场 8+2+1、大棚 6）；一期 **86 种作物**，二期起补到 **200 种**。
- **四个附属阶段都带地块**（阶段 2 / 5 / 8 / 9 分别 +3 / +2 / +2 / +1）：扩建必须看得见。早期版本把它们写成「只加作物」，玩家感觉不到「家变大了」，那它跟「多给 6 种菜」没有区别。
- **十个阶段各带一个新机制**（见 §3 表「新机制」列）：没有一个阶段是「只发作物不教东西」。这是打掉难度锯齿的关键——阶段 7 / 8 / 9 的挑战来自**规模风险 / 经济维护 / 产能管理**，而不是「作物变难种」。
- **四个阶段是「附属」而非新场域**（阶段 2 / 5 / 8 / 9）：它们是现有场域的扩建，跟着场域走，**不占独立解锁权重**——玩家的感受是「后院大了」而不是「又多一个地方」。
- **打破「一级一阶段」**：阶段 4（Lv4–5）、6（Lv7–8）、7（Lv9–10）、9（Lv12–13）各跨 2 级，一个等级可能解锁两批作物，也可能一级内同时推进两件事。
- **前 5 阶段 40 种（46%）**，不再是「两周放完一半内容」。

**六个场域 = 六种不同的失败模式**，不是数量堆叠：

| 场域 | 怕什么 | 风险画像 |
|---|---|---|
| 窗台 / 花箱 / 缸 | 什么都不怕 | **保底区**：事件免疫、冬季仍能种（惩罚软化），极端天气有退路 |
| 后院 | 季节 + 天气 | 温和：叶菜好养（阶段 4），木本花卉与香草园娇气（阶段 5/9） |
| 农场 | 季节 + 天气 + **整行灾害** | 收益区：回报最高但一场霜冻波及整片 |
| **大棚** | **只有温度** | **风险完全相反**：季节免疫（热带作物全年可种），但寒潮冻死、夏季不降温则热死 |

- 大棚是**唯一不怕季节的场域**，让「冬天种什么」有了除室内之外的答案——也是热带植物的唯一种植地点。
- 生态缸是「有维护成本的温室」：免疫一切但每周要补水，缸内专属作物只此一处可种。**新机制（周维护）安排在 Lv7–8 登场**，给玩家消化时间。
- **设施与作物绑定解锁**（阶段 2/8）：扩建不是白送的，它是这些作物能种的**前提**（大花盆才有香草的深根空间，农田设施才有经济作物的授粉与灌溉）。

## 4. 园丁等级与图鉴

**等级封顶 Lv100**，且**等级不再决定内容解锁**（见下方「等级与解锁解耦」）。等级只负责两件事：**展示成就** + **里程碑永久加成**。解锁阶梯只到前十个阶段（内容就那么多），之后靠**每 10 级一个里程碑**给东西——**不做 92 个解锁点**，那是玩家爬到一半就失去目标感的经典失败。

**进度（不落库，从日志与仓库推导）**

| 进度线 | 来源 | 权重 |
|---|---|---|
| 园丁 XP | 照料 +5（**每地块每日只计第一次**，重复照料照常给积分但不给 XP）；收获按阶位 15 / 25 / 40 / 60 / 90 / 120；新作物首收 +30 | 主线，约 95% |
| 图鉴深度 | 已收获作物数（每种 +0.5%）+ 套装完成度（每套 +3%） | 微调，压「只种一种」 |
| 连续活跃 | streak 天数（上限 30 天，每档递减计入） | 回归奖励，防弃坑玩家断层 |

> 「每地块每日只计第一次」是必要的护栏：36 块地 × 12h 冷却若按次计 XP，后期一天可刷 500+ XP，等级线三天顶穿、形同虚设。

### 4.1 等级与解锁解耦（V2 最重要的一次纠错）

**原设计是「等级决定解锁」**，即 `level = 1 + floor(sqrt(total / 12))`，Lv15 开温室大棚。
**实测下来这是错的**：

| 等级 | 公式要求的累计进度 | 实测第几天能到 |
|---|---|---|
| Lv3 | 48 | 第 1 天 |
| Lv7 | 432 | 第 4 天 |
| **Lv15（温室大棚）** | **2,352** | **第 6 天** |

`sqrt` 曲线在低段太平，**36 块地带来的进度增长远远追在它前面**——结果就是**一周打通全部十个阶段**，后面大半年没有新地方可开，满级前的内容全部提前见底。

**根因是一个公式背了两个职责**：既要当「成就等级」，又要当「内容闸门」。两者需要的曲线形状完全不同。

**V2 的解法是把两个职责拆开**：

| | 职责 | 曲线 | 满级周期 |
|---|---|---|---|
| **等级** | 展示成就 + 里程碑永久加成 | `level = 1 + floor(sqrt(total / 12))`，**不变** | 约 1 年 |
| **阶段解锁** | 决定新场域 / 新作物 / 新机制 | **独立的进度阈值表**（`content/unlock.json`） | 见下表 |

**解锁阶梯（进度阈值驱动，不是等级驱动）**

| 阶段 | 累计进度门槛 | 约合天数 | 地块 | 作物 | 同时解锁 |
|---|---|---|---|---|---|
| 1 窗台 | 0（初始） | 第 1 天 | +3 | 8 种 | 仓库 30 格 |
| 2 大花盆 | 200 | 第 3 天 | +3 | 6 种 | — |
| 3 花箱 | 600 | 第 8 天 | +3 | 6 种 | 混种 / **锦化**首现 |
| 4 后院 | 1,500 | 第 15 天 | +6 | 10 种 | 洒水壶 / 营养土 / **温度计**图纸 |
| 5 深土区 | 2,800 | 第 22 天 | +2 | 6 种 | 剪刀 / **湿度计**图纸 |
| 6 生态缸 | 4,800 | 第 30 天 | +2 | 10 种 | 隐性难度登场（两件仪表已就位） |
| 7 农场 | 9,000 | 第 50 天 | +8 | 12 种 | 整行灾害 |
| 8 农田设施 | 14,000 | 第 65 天 | +2 | 8 种 | 设施维护 / 授粉管理 |
| 9 扩充 | 20,000 | 第 85 天 | +1 | 6 种 | 多产地分散种植 |
| **10 大棚** | **34,000** | **第 120 天** | +6 | 12 种 | 温度管理 |
| 11+ | 50,000 起 | 第 165 天 | — | 回填 | 旧场景高级作物 |

- **「约合天数」按实测速率推算**：3 块地约 60 进度/天、9 块约 210、19 块约 400、27 块约 800、36 块约 1,900。它是校准参考不是承诺——玩家实际节奏（每天照料几次、有没有全家参与）会让天数浮动。
- **阈值表放 `content/unlock.json`**，与 `crops.json` 同级——策划能自己调，不用发版。
- **仪表必须在隐性难度之前**（§5.7 的硬顺序）：温度计在阶段 4、湿度计在阶段 5，所以阶段 6 缸里那些难养作物登场时，**玩家手上已经有仪表能读懂它们的问题**。

**解耦顺带解决了「Lv16–19 空窗」**：旧设计里 Lv15 开完大棚、Lv20 才有下一个里程碑，中间四级既没内容也没奖励。现在等级和解锁各走各的——**第 120 天开大棚时玩家已经 Lv54**，里程碑（每 10 级一个）在整个解锁过程中会命中 6–7 次，全程都有反馈。

**为什么不用「等级 + 进度」双闸门**：双闸门只是把公式的毛病藏起来——玩家仍然要凑两个数字，且等级那条永远是先到的那条，等于白加一层。直接用进度阈值更简单，也更好解释（「你累计照料收获了多少」比「你的经验值是多少」更贴这个游戏）。

### 4.2 图鉴加成与套装

**十个里程碑（Lv10 起每 10 级一个，每级都改一条规则，不是纯加数）**

| 等级 | 里程碑 | 改什么 |
|---|---|---|
| Lv10 | 仓库扩容 | 容量 30+10×(Lv−1) → **30+15×(Lv−1)**，解「满仓卡死」 |
| Lv20 | 图鉴套装 | 每收齐一套同阶段作物 +3% 成长（引入套装维度，见下） |
| Lv30 | 施肥流强化 | 施肥成本 −30%，营养衰减 72h → 48h |
| Lv40 | 惩罚放宽 | 霜冻只冻结露天 FIELD，室内与后院盆位免疫 |
| Lv50 | 冬季外场可种 | 错季成长惩罚再软化一档（×0.3 → ×0.5） |
| Lv60 | 工具折价 | 强化到 +5 的成本 −25% |
| Lv70 | 反季补种 | 错季卖价惩罚减半（×0.5 → ×0.25） |
| Lv80 | 高阶收益 | 每日照料 XP 上限提升 |
| Lv90 | 全局永久 | 全成长永久 +10% |
| Lv100 | 园艺宗师 | 称号 + 图鉴页展示全部作物原画 |

全部是纯函数 / 配置项，不新增内容类型、不新增表。

**图鉴加成（收集驱动，两层）**：每收获过 **1 种**作物 **永久 +0.5% 成长**（**硬顶 +33%**）；**每个变体再 +0.5%**（§5.4）；**每收齐一套同类作物再 +3%**。

> ⚠ **为什么不是 +1%**：作物从 37 扩到 86 后，若仍按 +1%/种，图鉴加成会到 +86%，把等级加成（+5%/级）完全压过去，两个永久来源的权重失衡。改成 +0.5% 后上限 +33%，与等级加成同量级，总量仍在 §10 的 ×3.0 硬顶内。

套装按三类维度切：同阶段（**11 套**）、同类别（食 / 赏 / 材，各 1 套）、全收集（1 套）。图鉴页同时是收藏页与长期目标页。

**满级之后靠什么保持新鲜**：不靠等级，靠**时间维度**的四层轮换——季节（§7，已内置，零成本）· 节气事件（§14.4）· 图鉴套装 · 周挑战（§15）。**内容年更量为 0**，因为轮换的原料是日历与既有配置。

## 5. 作物体系（一期 86 种 → 二期 200 种）

### 5.1 总量与参数化渲染

**上限不是美术，是配置行**。作物外观做成**参数**而非手绘资产：每种作物一行外观参数（茎高 / 叶数 / 果实形状 / 色相 / 花色 / 是否摇曳），6 个生长阶段由同一组参数插值。故一种作物的边际成本 ≈ **1 行配置 + 2 条 i18n**，不是 6 张图。

- **一期 86 种，全部现实作物**（虚拟作物与虚拟变体已整体移出，见 §5.3.1）。
- **室内要能养很多东西**（用户诉求）：阶段 1 + 3 就给 20 种家居植物，从「一盆小葱」到「鹿角蕨 / 空气凤梨」这种公认难养的——**难养不等于难做**，它的难在于湿度 / 光照 / 耐温区间（配置项），不在渲染。
- **三类用途**决定数值与出口：**食**（卖出 / 入厨接现有菜谱，产量高单价低、季节敏感最强）、**赏**（图鉴 / 徽章，产量 1~2、单价高、靠图鉴吃复利）、**材**（加工链 → 工具强化 / 设施，原料不出售）。
- **补到 200 种的两条路**：① 前面场景的**高级作物**（月季品种 / 多肉品种 / 兰花品种）——回到已解锁场景挖深度；② **品种层**（cultivar）——同物种下的园艺品种只改 `season_mult` / `price` / `trait_pool` 子集，**形态继承父种**，边际成本 1 行 JSON + 2 条 i18n，**零新增形态**。66 套形态服务 200 个条目。

### 5.3 变体体系（现实植物学变体）

变体是**属性修饰**，改渲染参数与卖价系数，**不动成长逻辑**——这是它便宜的原因。

#### 5.3.1 三个位点，不建变体表

| 位点 | 取值 | 渲染方式 |
|---|---|---|
| 花型 FLOWER_FORM | 单瓣 / 重瓣 / 球重瓣 / 针垫 / 垂瓣 / 猪笼 / 平口 | 花瓣按层重复叠加（1~3 层） |

> **决策：去掉「虚拟变体」**（发光 / 霜纹 / 镜光 三个取值）。理由有三：① 发光要靠外发光滤镜，是一套独立渲染管线，与其余取值不同源；② 镜光叶在扁平风格里几乎看不出来；③ **虚拟作物整体移出作物表**，全部用**现实作物补位**——既服务于「作物补到 200」的目标，也避免现实保真（§5.6）与虚拟设定打架。

#### 5.3.3 稀有度与保底

| 档 | 权重 | 例 | 卖价系数 |
|---|---|---|---|
| 常见 | 75% | 单瓣 / 全绿 / 白粉黄 | ×1.0 |
| 少见 | 20% | 重瓣 / 白边 / 橙红 | ×1.3 |
| 稀有 | 5% | 斑叶 / 白化 / 渐变镶边 | ×1.8 |

**保底**：同一作物每 **5 次收获**至少出一个「少见以上」——非酋不至于空手，收集节奏也可预期。

#### 5.3.4 图鉴白名单 vs 组合爆炸

三位点自由组合理论上有几十种，但图鉴页不能全展示：**图鉴只认白名单**（每种作物预设 4~6 个常见 + 稀有组合，见 5.3.2 末列）。名单外组合照旧**能长、���卖、不进图鉴**——既有惊喜，又不必预设全部组合。

#### 5.3.5 确定性 roll

- 变体在**播种时 roll 并落地块 `variant` 列**，从发芽期就展示叶纹——玩家看的不是「结果揭晓」，是「这株是什么」。
- roll 用 `(plotId + harvestCount)` 作种子，**同一株刷新页面不变样**；否则前端一刷新就换色。
- 定向培育（后期可选）：同种收获 N 次 + 积分换指定变体，把随机变成可规划。

### 5.4 变体对数值的影响（克制）

- **不影响生长速度**——否则「刷变体」会绕开轮作机制，季节 / 土壤的设计就废了。
- 只影响**卖价**（§5.3.3 系数）与**图鉴计数**。
- 图鉴：品种每种 +0.5%（§4），**变体每个 +0.5%**。

### 5.5 繁殖：扦插与杂交

两者都**不新增表**，都走 `content/recipes.json`（`type=PRUNE` / `type=CROSS`）+ 现有的「占用地块 → 扣仓库 → 写 plot」三段流程。

#### 5.5.1 扦插（把随机变成可复现）

变体是随机 roll 的，若无扦插，图鉴条目里绝大部分是不可复现的抽奖。扦插专治这一点。

| 项 | 值 |
|---|---|
| 输入 | 母株同种果实 ×2（或同种 ×1）+ 园币 10 |
| 输出 | 新地块 = **同 `crop_code` + 同 `variant`**，直接定型 |
| 生长 | ×0.6（扦插本就比播种快，植物学上也对） |
| 保底 | **不消耗** §5.3.3 的「每 5 次保底」计数 |
| 图鉴 | 只对**已有**变体有效；仍须首次 roll 才发现——**发现归发现，量产归量产** |

#### 5.5.2 杂交：只做两种，不做「随机合出随机新种」

**A. 定向杂交**——指定亲本出指定子代，就是菜谱：番茄 × 辣椒 → 灯笼椒。加 20~30 行 `type=CROSS` 配置，**零新代码**，且这才是真实园艺的做法（按配方杂交，不是碰运气）。

**B. 属性融合**——子代从双亲各继承一个位点。变体三位点（§5.3.1）已是一等公民，故规则只要一个纯函数：

```
child.crop = crossable(a.crop, b.crop)      // 亲本兼容表
child.变体  = pick(a.trait_pool ∩ child.trait_pool)   // 交集约束
            + pick(b.trait_pool ∩ child.trait_pool)
```

交集那一步是关键：约束「合出来的性状必须落在该作物的 `trait_pool` 里」，不会造出「会发光的番茄」。白名单外组合照旧**能长、能卖、不进图鉴**（§5.3.4 规则原样复用）。

亲本兼容表（**一张配置表，非业务表**）：同阶段可交、跨 1 阶段可交、五阶只与五阶可交，约 15 行。

#### 5.5.3 绑死约束（否则会瓦解整个解锁阶梯）

如果杂交能无限复制最好的东西，十个阶段的阶梯就白设了。规则：**杂交产物是侧支，不是上位替代**。

- 杂交子代**不进主经济阶梯**：不入 §5.2 阶段表、不参与错季轮换、卖价按固定档（介于四阶与五阶之间）、无季节敏感度。
- 价值全部导向**加工链与图鉴**——新配方、套装、徽章，也就是 §4 那个「解锁完了没事干」的空档。
- 「可杂交」本身是**图鉴解锁项**，不是开局就全开——杂交是收集后期的奖励，不是开局捷径。

### 5.7 难度可见性分层（顺序设计的第一原则）

> 用户关切：「过早地提前室内高难度植物是不是太难了」。**对——这是设计错误。**
> 纠正的关键是：**「难」不等于「难伺候」。**

**隐性难度的正确前置条件**：玩家已经能读懂状态徽章 + 手里有应对道具。

反例是真实存在的：早期版本让「鹿角蕨湿度不足就不长」在阶段 3 的花箱里登场，那时玩家既没有湿度计、也没见过任何一次可见难度——**看不到为什么不长**，只看到进度条不动。那是挫败，不是挑战。

**V2 的排法是把它压到阶段 6 的生态缸**，而温度计在阶段 4、湿度计在阶段 5 就已给到（§4.1 解锁表），所以缸里那批难养作物登场时，仪表早已在手。

**分层如下**：

| 阶段区间 | 难度类型 | 具体机制 | 为什么可以提前 |
|---|---|---|---|
| **1–3** | **零隐性** | 只有缺水（明确提示）、土壤错配（×0.7，标签直接写） | 都是一眼可见的百分比或明确状态，不需要任何新知识 |
| **4–5** | **可见难度** | 天气事件（干旱 / 霜冻）、同科重茬、遮荫、虫害 | 全部以「进度条卡住 + 徽章 + %」呈现，玩家知道要解决什么，且都有对应解法（浇水 / 换科属 / 装支架 / 用驱虫剂） |
| **6+** | **隐性难度** | 湿度 / 光照阈值（鹿角蕨、空气凤梨、菖蒲、栀子、茉莉、可可） | 此时已有温度计 + 设施 + 图鉴，能读懂；且前置的可见难度已经教会玩家「出问题就去查条件」 |

**配套的三条做法**：

1. **隐性难度必须给「可读的仪表」**：土壤含湿度、光照时长这两项在 §18 已规划为「温度计」工具的信息面板。**没有仪表就不上隐性难度**——这是硬顺序，不是建议。
2. **「锦化」正向挑战从阶段 3 就给**（§5.2 阶段 3）：它不需要玩家懂任何新规则（就是持续照料正确），却是明确的追求目标。早期就需要这种「努力有回报」的反馈，来对冲隐性难度的推迟。
3. **隐性难度作物与「场地专属」解绑**：不能出现「缸 = 难养」这种关联——否则玩家会把「难」记在场地头上而不是作物上。所以栀子 / 茉莉虽然是难养，却归花箱（阶段 11+ 回填时才给），而缸里仍有苔藓 / 碗莲 / 捕蝇草这类「场地专属但好养」的作物。

> **反面教训**：把「高级难养」全压在最后一个阶段，会让中期（Lv4–Lv8）毫无挑战；反过来把它全堆在前中期，会让新玩家在还没学会基本循环时就被劝退。正确的分层依据是**玩家手上的工具箱**，不是时间轴。

### 6.1 地块间作与连作（结构性杜绝单一作物）

> 这是**机制层面**保证「别只种一种」的地方——不靠提示文案，靠空间与土壤的物理约束。

**布局**：场域是网格，相邻 = **正交**（上下左右），斜角不算。

| 场域 | 网格 |
|---|---|
| 窗台（小盆）/ 窗台扩建（大盆） | 1 行 × 3 列 / 1 行 × 3 列 |
| 花箱 | 1 行 × 3 列 |
| 生态缸 | 1 行 × 2 列 |
| 后院 / 后院深土区 | 3 行 × 2 列 / 2 行 × 1 列 |
| 农场 / 农田设施（经济垄） | 4 行 × 2 列 / 2 行 × 1 列 |
| 大棚 | 3 行 × 2 列 |

**合计 36 块**（3+3+3+2+6+2+8+2+1+6）。单场域最多 10 块（农场），单行最多 4 列——**网格刻意做得窄**：园丁 App 是竖屏手机，窄网格才放得下地块卡又不横向溢出。

> **⚠ 性能影响**：36 块地同时渲染是性能基线（V1 只有 6 块）。每块含土层 + 作物 + 状态徽章。客户端是 **Cocos**（§18.1）：地块卡走 **Prefab 实例化 + 对象池复用**（不要每次 `instantiate` 新建节点），非当前场域的贴图按**分包/目录按需加载**（见 `CocosCreator资源管理规范.md` §四）。

`slot_no` → (row, col) 由 `content/venues.json` 的网格规格推导，**不加列**。相邻效应**在播种时结算并冻结**（不做移栽），保持「一次决策」的干净。

**三个机制**：

| 机制 | 判定 | 效果 |
|---|---|---|
| **相邻互利** | 正交邻居命中「伴生对」（`content/companions.json`） | 每对 **+8%** |
| **相邻相害** | 薄荷园（化感，抑制他植）/ 向日葵田（化感） | **−10% / −8%** |
| **遮荫** | 高作物（玉米 / 向日葵 / 香蕉 / 芭蕉）紧邻低作物 | 低作物 **−8%** |
| **同科重茬** | 同一地块连续种**同科**作物 | ×0.85 → ×0.70 → **×0.55**（地板） |

- 单块地相邻总修正**钳制在 [−20%, +15%]**——防止四周全是好邻居叠成 +32%。
- **重茬倍数只作用于成长**（不计产量）——否则惩罚过重，会让人直接弃耕。

**重茬是最狠的一条**：番茄 / 土豆 / 辣椒**同属茄科**，三阶段都是主力——不轮作就连种多块地全在掉产；唇形科横跨五阶（薄荷 / 罗勒 / 百里香 / 迷迭香 / 薰衣草），把香草全堆在花箱会连吃三次衰减。这两条自然逼出分散种植。

## 7. 季节系统

- **季节是纯函数**：月份 → 季（北半球 3–5 春 / 6–8 夏 / 9–11 秋 / 12–2 冬），不落库、不给季节换场域补表。
- **倍率在作物配置里**：`season_mult` 存本命季倍率（1.0~1.3）、平季（0.6~0.8）、逆季（0.2~0.4）。暖季作物夏 1.3 / 冬 0.2，冷季作物春秋 1.2 / 夏 0.6，长季作物波动小（0.9~1.1）——**同一作物当季与逆季收益差 3~6 倍**，这是轮作的第一驱动力。
- **场域软化**（室内不至于寸草不生）：逆季倍率在窗台 / 花箱按 **×0.5** 取下限、在生态缸按 **×0.7**；保温棚再 ×1.25。**大棚季节免疫**（热带作物不受此影响）。
- **错季卖价 ×0.5**：非本命季收获的果实品相差，卖出打折——第二次惩罚，让「种错季」双重亏本。

## 8. 天气、气温与事件

天气沿用 `WeatherService` 归一化 condition，**只作用于当前状态推导**（沿用 V1 口径：不追溯历史天气、不引后台定时任务）。事件同样由「当前天气 + 地块状态」推导，不存状态位。

**照料倍率（沿用 V1 表）**：

| condition | 浇水 | 晒太阳 | 自动补水 |
|---|---|---|---|
| clear | 1.0 | 1.5 | ✗ |
| cloud | 1.0 | 1.0 | ✗ |
| rain | 1.5 | 0.5 | ✓ |
| snow | 0.8 | 0.3 | ✓ |
| fog | 0.9 | 0.7 | ✗ |
| thunder | 1.3 | 0.4 | ✓ |

**天气事件**（仅作用于室外场域，室内场域免疫）：

| 事件 | 触发（推导） | 效果 | 对策 |
|---|---|---|---|
| 干旱 | 室外地块 + 当前晴 + 距上次浇水 > 48h | 成长 ×0.7 | 浇水即解；遮阳棚免疫 |
| 霜冻 | 室外地块 + **气温 ≤ 0℃**（见 §8.1） | 成长冻结（进度停走） | 保温棚 / 抗寒剂免疫；转暖自解 |
| 生态缸失水 | 缸内地块距上次补水 > 7 天 | 成长 ×0.5 | 补水（`mist`，+2 园币，缸内专用） |

### 8.1 气温双轨（家庭所在城市的当日气温）

> 用户诉求原文：「天气用当前家庭设置的城市当天所在的气候温度天气来考虑」。

**取数已现成**：`QWeatherProvider.current()` 已返回 `{condition, temp, text, city}`，`temp` 取自 `now` 接口（非预报）；家庭定位走 `family.weather_lat / weather_lng / weather_city`（`FamilyPlantService.weatherOf` 已在读）。V1 只用 `condition` 是因为只有一棵树，不需要温度。

| 判定 | 阈值（可调） | 效果 | 现实依据 |
|---|---|---|---|
| **霜冻** | `temp ≤ 0` | 室外地块冻结 | 真霜冻就是 0℃ 以下——比「12 月 + 下雪」的日历判定准得多 |
| **低温胁迫** | `temp < 作物耐寒下限` | 室外成长 ×0.6 | 有霜 / 无霜植物的耐温差异 |
| **高温胁迫** | `temp > 作物耐热上限` | 成长 ×0.7 | 35℃ 以上番茄停止坐果 |
| **昼夜温差** | 当日最高−最低 < 5℃ | 甜度 / 果实品质 −10% | 真实农业结论（大温差利于糖分积累） |

每种作物的 `temp_range {min, max}` 写进 `content/crops.json`。

**⚠ 取数口径（避免进度倒退的 bug）**：成长按「累计分钟 × 倍率」算，一天的倍率必须**日内恒定**。

| 方案 | 判定 |
|---|---|
| 每次读取取**实测**温度 | ❌ 昼夜波动会让「半夜刷新进度倒退」，数值不可信 |
| 定时任务采一次存一行 | ❌ 要新表 + 定时任务，破坏「不引后台任务」底线 |
| **取当日预报均温（采用）** | ✅ `getDetail()` 已返回日预报，取 `tempMin/tempMax` 均值；无新表、无定时任务、天然恒定 |
| 无天气数据时 | 回退按季节查表给默认均温，不阻断游戏 |

> 霜冻改用气温判定后，「1 月没下雪的暖冬」不再误判，而「11 月一场寒潮」会真的冻苗——**原日历判定直接删掉**。

> **现实保真红线**（同 §5.6）：只做常识级判定（0℃ 结冰、35℃ 高温）。**不做**「25℃ 时番茄光合作用下降 12%」这类半专业公式——没人验证得了，只会让懂行的人觉得这游戏胡编。

### 8.2 作物状态异常（软失败：会病不会死）

> **铁律：植物永远不会死。** 家庭陪伴场景下，让孩子看着自己的植物枯死是不可接受的。只做「状态不佳」——可逆、有代价、看得见。

**全部为纯函数推导，不落状态位**（`water_count + sun_count` 与 `last_*` 时间戳已够）。

| 状态 | 触发（推导） | 成长 | 产量 | 解法 |
|---|---|---|---|---|
| **徒长** ETIOLE | 连续 2 天非晴（cloud/rain/fog/snow）且 48h 内未晒太阳 | ×1.0 | **−30%** | 晒太阳 ×2（外观变细长） |
| **缺水** THIRSTY | 距上次浇水 > 48h | ×0.7 | — | 浇水 |
| **灼叶** SCORCH | `temp ≥ 35` + clear + 露天 + 无遮阳棚 | ×0.6 | −20% | 遮阳棚 / 少晒太阳 |
| **沤根** ROOT_ROT | 雨后 24h 内又浇水（排水不良） | ×0.5 | −20% | 停浇 24h + 晒太阳通风 |
| **虫害** PEST | `temp 25~32` 且连续阴雨 ≥ 2 天 | ×0.8 | 持续 −5%/天 | 剪刀修枝（1 次/天）/ 驱虫剂 |
| **⭐ 锦化** CHIMERA | 无任何异常 + 距上次照料 ≤ 24h + 本茬照料 ≥ 3 次 | **×1.15** | **+20%** | 保持；持续 72h 或遇异常即失效 |

- **锦化是唯一的正向状态**，且是「养得好」的奖励：照料次数够、状态健康 → 植株泛金光，成为「稳妥必收」的保险。72h 后或一旦触发任何异常即失效——**不能无脑留着**。
- **虫害不做累积计数**（会需要历史表），取固定 ×0.8。
- **驱虫剂**（消耗品）：`薄荷 ×2` 合成——薄荷驱虫是真实的，同时让薄荷那个「化感 −10%」的负面位**有了正面出口**，不显得是纯坑。
- **剪刀获得第二用途**：修枝清虫（每日 1 次），强化到 Lv5 后修枝效果更好。

**UI**：地块卡状态徽章扩为 `顺季 / 逆季 / 干旱 / 霜冻 / 待补水 / 徒长 / 灼叶 / 沤根 / 虫害 / 锦化`，同一套徽章机制加取值即可；锦化用金色柔光边框与普通异常的红/橙边框区分开。

### 8.3 收获物形态（类别决定出口）

作物类别不只是标签，它**决定收获物的形态与可用出口**：

| 类别 | 收获物 | 可用出口 |
|---|---|---|
| **食** EDIBLE | 鲜果 FRESH | 市集卖出 / 入厨进冰箱（最自由） |
| **赏** ORNAMENTAL | 花束 BOUQUET | 入厨不可 / 出售价 ×1.2 / 预留「制干花 → 庭院摆件」（§14.5） |
| **材** MATERIAL | 材料（花汁 / 纤维 / 树液 / 亚麻） | **不可卖**，只能进加工链 → 工具强化 / 设施 |

这条规则顺带解释了经济设计：材料类作物不产生园币，它们的价值在配方里的投入端——避免了「种材料也顺便刷钱」。

### 8.4 灾害预警（§14.4 写了却没定义的那一半）

> §14.4「霜降」条目早就写了「露天地块**霜冻预警**」，但全文没有任何一处定义它长什么样、什么时候推——**这是补一个写了没做的洞**，不是加新功能。

**触发（推导，零状态位）**：当日预报 `tempMin ≤ 0℃` + 露天场域有在种作物 + 该场域未盖保温棚 → **推一条家庭通知**。

| 项 | 取值 | 为什么 |
|---|---|---|
| 数据源 | `QWeatherProvider.getDetail()` 的 `tempMin` | **已现成**（§8.1 已在用它做气温双轨），零新表零定时任务 |
| 内容 | 「今晚最低 −2℃，3 块露天地块会霜冻。盖保温棚（120 园币）或用抗寒剂（薰衣草 ×1）」 | **直接给对策**——只报灾不给解法的提醒会变成噪声 |
| 时机 | **打开花园页时读接口推导**（无定时任务，符合 §8 口径），当天首次满足即推、一天最多 1 条 | 幂等靠 `garden_world.settings.warned_date` 记，不建表（§25.4） |
| 通知类型 | `NotificationService` type=`plant` | 沿用 §15 现有通道 |
| 干旱顺带 | 距上次浇水 > 48h + 当日晴 → 同一时刻并成一条 | 两个预警合并成「今晚照料清单」，不刷屏 |

**边界**：

- **预警是提醒，不是代劳**——仍需玩家自己盖棚 / 用抗寒剂，不做任何自动操作（家庭产品里自动操作会吃掉「我照顾了它」的成就感）。
- **不做连续推送**。今天已经提醒过、明天还是 0℃，只在**条件重新满足且隔了 ≥1 天**时再推一次；反复催促是家庭产品最招人烦的行为。
- **室内场域不报**（免疫，见 §8）；已盖保温棚的地块不报——**提醒的价值在于它可行动**。
- 推送时**只报受影响的地块数**，不逐块列（36 块地全冻时列出来只会没人看）。

## 9. 营养系统（沿用 V1）

- 营养 0–100，**按地块**推导：施肥后 100，72h 线性衰减到 20；从未施肥基线 50。
- 营养 → 成长倍率 `0.7 + 营养 × 0.006`（50→1.0 / 100→1.3 / 0→0.7）。档位展示：≥75 肥沃 / ≥40 正常 / <40 贫瘠。
- **施肥**：−15 园币（家长规则 `plant_fertilize` 可调）+ 立即成长加成 360min × 营养土倍率 + 营养重置 100；冷却 12h / 地块。

## 10. 成长模型（总公式，一处收口）

```
成长速率倍率 = 1
  × 时间比例换算(R,§12.3)          R = 现实分钟 / 游戏小时,全局唯一
  × 土壤匹配(§6)                 1.2 / 1.0 / 0.7
  × 季节倍率(§7,含场域软化)       0.2 ~ 1.3
  × 气温适配(§8.1)               0.6 ~ 1.0
  × 营养速率(§9)                 0.7 ~ 1.3
  × 间作修正(§6.1)               相邻合计钳制 [−20%, +15%]
  × 同科重茬(§6.1)               1.0 / 0.85 / 0.70 / 0.55
  × 状态异常(§8.2)               徒长 ×1.0 / 缺水 ×0.7 / 灼叶 ×0.6 / 沤根 ×0.5 / 虫害 ×0.8 / 锦化 ×1.15
  × (1 + 0.05 × (园丁等级 − 1))   永久,Lv100 = ×5.95
  × (1 + 图鉴百分比 / 100)        永久,硬顶 ×1.33
  × 短效 buff 乘数(§14)          ≤ ×1.5
  × 事件乘数(§8)                 干旱 ×0.7 / 节气(§14.4) / 协作(§15.1) ×1.05~1.10
  × 设施修正(保温棚冬季 ×1.25 等)
  ─────────────────────────────
  总乘数硬顶 ×3.0(超出按 3.0 截断)

累计成长分钟 = 现实经过分钟 / R × 总乘数(缺水 / 霜冻 / 事件期间冻结) + 累计照料加成
照料加成 = Σ(浇水 +120 / 晒太阳 +120 / 补水 +120 / 施肥 +360) × 各自天气 × 各自工具倍率
收获产量 = round(作物产量区间随机中值 × 土壤匹配 × (1 + 0.08 × 剪刀等级) × 产量buff × 状态产量系数)
阶段 = 按「累计成长分钟 / 作物基础时长」的 6 段比例:0 / 0.1 / 0.35 / 0.6 / 0.85 / 1.0
      SEED → SPROUT → SEEDLING → BUD → FLOWER → FRUIT(可收获)
```

- 作物基础时长 = `content/crops.json` 的 `growth_hours × 60`，因此不同作物阶段节奏自然不同（24h 的小萝卜一天走完，192h 的芒果走八天）。
- **R 是全局主旋钮**：只缩放总量，作物间相对价值不变（总量与结构分离，原则 8）。换 R 无需迁移——`planted_at` 存现实时间戳，进度是纯函数。
- 照料冷却**下沉到地块**：浇水 / 晒太阳 12h / 地块（V1 是 6h / 家庭）——多地块时代家庭级冷却会让后面的地块永远轮不到。
- 阶段、营养、进度、等级、间作修正**全部实时推导**，读接口算，不落库（沿用 V1 原则 1）。重茬只记 `plot.prev_family` 一个字符串（播种时写入、换非同科时清空），无需连作历史表。
- 图鉴与套装倍率以 `(1 + 图鉴百分比 / 100)` 一项计入；节气事件（§14.4）、协作加成（§15.1）各自是独立的一行乘子，不塞进同一项，便于单独调参与封顶。

## 11. 家庭仓库（收获即入库）

> 用户诉求原文：「仓库是家庭公共的仓库，收获后进入家庭仓库里」。

- 表 `garden_inventory(family_id, item_code, qty)`，**家庭级共享、单一仓库**（不按人分仓）。
- 容量：`30 + 10 × (等级 − 1)`，Lv100 = 1020 格；**满仓禁止收获**（409，提示先清理）——逼玩家处理收成，而不是无限堆。
- 收获 → 果实按 `果实产量` 直接入仓（同码堆叠）；种子**不入仓**（播种时直接扣园币买种，少一套物品类型）。
- 仓库是**家庭共享**的，但卖出后进的是**操作者本人的园币钱包**（§12.1）。
- **三个出口**：
  1. **市集** → 挂单给家人，或按参考价卖给系统（园币入个人钱包，§12.2）；
  2. **入厨** → 写入 `family_item(type=INGREDIENT)` 进冰箱（复用厨房保质期 7 天逻辑），从而**接上现有菜谱 / 菜单**；
  3. **加工** → 花汁 / 纤维 / 树液等材料，供工具强化与食谱使用。
- 鲜果**不做保质期**（免损失焦虑）；只有入冰箱后才受厨房保质期约束。

## 12. 经济系统（园币 · 市集 · 积分闸门）

> 用户诉求原文：「增加游戏内货币，增加市集……避免游戏内专区的积分过高，破坏了现实积分兑换的平衡」。
> **背景**：ihomy 的积分来自内容创作（博客 10 / 日记 8 / 照片 2 / 视频 15 / 签到 5），家长常把积分当零花钱对标（1 积分 ≈ 1 元）。若农场直接发积分，稳定产出将同时毁掉「写内容换积分」的激励与积分商城的定价基础。

### 12.1 园币：币种隔离 + 单一受控出口

- **园币**是园内唯一流通货币，**个人钱包**（`family_id + player_uid`）——与「仓库 / 工具 / buff / 等级家庭共享」相反。理由同真实家庭：**共用冰箱、各自零花钱**；也让「谁把家里的果子卖了」有明确归属。
- **积分不可逆**：`积分 → 园币` **不通**。积分来自内容创作，不能反向流回园内稀释产出。
- 家长可在设置页**完全关闭**积分闸门（不想玩积分的家庭）。

**收支**：

| 方向 | 内容 |
|---|---|
| 入 | 市集卖果实（主）、烹饪成品、照料每日 +2 园币/次（与照料同冷却）、图鉴套装奖励 |
| 出 | 种子、阶段解锁、施肥、设施、工具强化、配方、扦插 |
| → 积分 | **唯一出口**，见 §12.3 |

> 参考价 = `单果价 × 变体稀有度系数(§5.3.3) × (错季 ? 0.5 : 1) × 节气系数`。变体只在这一层起作用，**不影响生长**——否则「刷变体」会绕开轮作机制。

**作物阶段单价（园币，明细见 §5.2）**：

| 阶段 | 种子价 | 单果价 | 典型单轮毛收入 |
|---|---|---|---|
| 一（室内） | 10~12 | 6~14 | 12~30 |
| 二（后院） | 20~60 | 18~48 | 40~200 |
| 三（扩容） | 14~20 | 15~16 | 30~60 |
| 四（花箱） | 40~74 | 34~64 | 70~180 |
| 五（农场） | 120 | 25~150 | 100~900 |
| 六（设施） | 120~130 | 38~92 | 80~500 |
| 七（缸） | 26~200 | 30~150 | 30~300 |
| 八（扩充） | 120~130 | 40~100 | 100~500 |
| 九（大棚） | 200~240 | 120~240 | 200~700 |

**支出项**：阶段解锁 200 / 400 / 800 / 1500 / **3000**；施肥 15；遮阳棚 80 / 保温棚 120（每地块，一次性）；工具强化见 §13。

**调参入口**：作物价签与季节矩阵在 `content/crops.json`，其余在 `PlantConst`；经济异常先改「单果价」一列，不动代码。

### 12.2 市集：家庭内循环 + 系统保底

| 机制 | 规则 | 为什么需要 |
|---|---|---|
| **成员挂单** | 上架仓库物品、设园币单价，其他成员购买，成交双方入日志 | 「合种共同培育」——**家庭就是市场** |
| **系统收购** | 果实随时按参考价卖给系统 | **保底出口**，否则「挂单没人买」会卡死经济 |
| **系统代售** | 系统常挂种子 / 肥料 / 工具清单（园币购买） | 园币的稳定入口，也给阶段解锁一条攒钱路线 |
| **⚠ 价格上限** | 挂单价 ≤ 系统参考价 **× 3** | **家庭保护**：防止不识字 / 不知情的成员花 9999 买一个 6 园币的萝卜 |
| **挂单时效** | 48h 自动下架 | 不做无限期挂单占位 |

- **家人交易与系统收购同价 → 无价差 → 没有套利空间**；价格波动只来自变体 / 季节 / 节气这三个已设计的维度。
- **不做**成交税（园币无外部价值，抽税只增边界情况）；**不做**家族间交易（家庭隔离是项目铁律）。

### 12.3 积分闸门：三重封顶 + 可调时间比例

**设计目标而非安全阀**：经济数值应调到「正常玩刚好打满 20 分/天」——那上限自带解释力，不需要例外条款。

| 项 | 值 | 说明 |
|---|---|---|
| 汇率 | **10 园币 = 1 积分** | 园币是小单位（角/分关系），读起来自然 |
| 个人日上限 | **20 积分** | ≈ 300 元零花钱的 20% |
| 家庭日上限 | **40 积分** | 双人玩刚好打满，三人自然分流 |
| 家长可调范围 | 1 ~ 100 积分/天 | 按自家 allowance 折算，设置页给「建议 = 零花钱 20%」计算器 |
| 打满后 | 园币照常在花园内使用，只是不再累积积分 | 文案须写「已达今日额度，明日恢复」——**孩子不该因到上限被惩罚** |

**时间比例 R（全局主旋钮）**：`R = 现实分钟 / 游戏小时`，作用于**所有**作物。

```
游戏经过小时 = 现实经过分钟 / R
```

| 档 | R | 1 现实日 = | 24h 作物 | 144h 南瓜 | 适用 |
|---|---|---|---|---|---|
| 快 | 0.5 | 2 游戏日 | 半天 | 3 天 | 碎片时间 / 低龄孩子 |
| **标准** | **1** | 1 游戏日 | 1 天 | 6 天 | 默认 |
| 慢 | 2 | 0.5 游戏日 | 2 天 | 12 天 | 高龄孩子 / 不常看 |

- 进度是纯函数推导（`planted_at` 存现实时间戳），换 R **无需数据迁移**，历史作物自动按新比例继续长。
- R 只缩放**总量**，作物间相对价值不变（同步缩放）——总量与结构分离（原则 8）。
- **⚠ 唯一的坑**：从慢(2) 切到快(0.5) 会让在地作物瞬间跳 4 倍进度，表现为「一觉醒来全熟了」。对策：**单次调整限幅 ±100%（最多 2 倍 / 0.5 倍）+ 24h 冷却 + 切换确认弹窗**（提示「在地作物进度将按新比例重算」）。

**校准表**（占位值，R=1、成熟农场约 12 块在种、平均倍率 0.8）：

| 阶段 | 生长 | 产量 | 单果价 | 园币/日/株 | 单块日积分 |
|---|---|---|---|---|---|
| 一 | 24h | 2~3 | 6 | ~15 | 1.5 |
| 二 | 48h | 2~3 | 15 | ~25 | 2.5 |
| 三 | 96h | 2~3 | 32 | ~37 | 3.7 |
| 四 | 72h | 3~4 | 40~48 | ~58 | 5.8 |
| 五 | 136h | 1~6 | 25~150 | ~40~90 | 4~9 |

成熟期（5 块五阶 + 5 块四阶）≈ 500 园币/日 → **50 积分/日/家庭**，双人各 25 —— 上限（40 家庭 / 20 个人）在此**正好咬住**：正常玩会打满，超玩被截。

> ⚠ **阶段间日收益刻意不单调**（五阶周期长、日收益低于四阶）：高阶靠**单块价值**与**解锁门槛**取胜，不靠日收益碾压，否则玩家会无脑种满高阶。真实平衡须靠实测调这张表。

**没有观测方案 = 永远校准不了。** `garden_stat`（§16.4）每日一行，是唯一的校准数据源。

| 指标 | 算式 | 健康区间 | 触发校准的信号 |
|---|---|---|---|
| **兑换触发率** | `points_out>0 的天数 / 活跃天数` | 40~70% | <30% = 园币太紧；>90% = 上限形同虚设 |
| **人均日园币** | `coin_in / 活跃家庭数` | 见校准表 | 低于目标 50% = 产出不足 |
| **各阶段地块占比** | `plant_cnt` 按 `crop_code` 分组 | 五阶 ≤60% | 任一阶段 >70% = 结构失衡 |
| **同科重茬触发率** | `plot.prev_family == 新科` 的播种占比 | 20~50% | <10% = 重茬没被感知；>70% = 惩罚过重 |
| **异常状态出现率** | 有状态的地块 / 全部地块 | ≤30% | >50% = 天气事件过苛，会劝退 |
| **图鉴完成度分布** | `garden_codex` 行数 | 中位 ≥15 | 中位 <8 = 内容太多或解锁太慢 |
| **仓库积压** | `SUM(qty)` / 容量 | ≤80% | 长期 >95% = 卖价太低或出口太少 |

**在哪看**：复用运维页现成的 charts 基建（`/ops` 的 timeline / type-distribution 那套，§4.6），新增一个「游戏域-花园」分组即可，**不新建统计框架**。

**校准动作**（改一处，不动代码）：

| 信号 | 改哪里 |
|---|---|
| 产出不足 | `content/crops.json` 的 `fruit_price` 列 |
| 上限打不满 | `garden_world.settings.daily_points_cap`（家长可自调，**先看是不是家长设低了**） |
| 结构失衡 | `content/crops.json` 的 `tier` / `season_mult` |
| 重茬过重 | `PlantConst` 的 `ROTATION_PENALTY` |
| 变体无感 | `content/crops.json` 的 `trait_pool` / `VARIANT_PRICE_FACTOR` |

> **校准纪律**：单周数据不调。家庭数少时波动大，**至少攒 30 个活跃家庭 × 14 天**再动数值，否则会把噪声当信号。

### 12.4 家长可调参数（只 2 个）+ AI 建议入口

| 参数 | 存储 | 范围 |
|---|---|---|
| 时间比例 R | `garden_world.settings.time_ratio` | 0.25 ~ 4，单次限幅 ±100%，24h 冷却 |
| 日积分上限 | `garden_world.settings.daily_points_cap` | 1 ~ 100 |

- **汇率不暴露给家长**（太细碎，一调就崩平衡）。家长可直接手调。
- **AI 建议入口**：复用现成 `AiService`（`resolveChain` / `resolveForFeature`），**不建新管线**。家长用自然语言说目标 → AI 输出结构化参数：
  > 「孩子 8 岁，每天最多玩 10 分钟，不想让他刷太多分」→ `{"timeRatio": 2, "dailyCap": 10, "note": "慢档 + 10 分/天封顶"}`
- AI 只是给建议起点，家长确认后才写入 `garden_world.settings`。沿用现有限制：**家庭级 AI 须家长先加模型再绑定**（`sys_family_ai_feature`）。
- 入口位置：设置页「花园设置」，**仅 OWNER 可见**；⚠ 存储落点是 `garden_world.settings`（JSON 列），**不是 `sys_parameter`**——后者是全局表（无 `family_id`）且值上限 500 字符，且用它做家庭隔离等于把世界设置绑死在 ihomy 上（§25.4）。**不新增表**。

**三条经济规则**：
1. **错季双重惩罚**（成长慢 + 卖价半），轮作是最划算的策略；
2. **照料 12h 地块冷却**——多地块下频率可控，堵死刷分；
3. **家长兜底**：`family_points_rule` 花园分区可关闭积分发放；§12.3 的 `daily_points_cap` 是第二道闸。

## 13. 工具、设施与强化

**工具（家庭级，可强化 +1~+5，不磨损、不绑定地块）**：

| 工具 | 效果 | 每级 | 满级 | 图纸 |
|---|---|---|---|---|
| 洒水壶 | 浇水成长加成 | ×(1 + 0.10 × 等级) | ×1.5 | Lv4 |
| 营养土 | 施肥成长加成 | ×(1 + 0.15 × 等级) | ×1.75 | Lv4 |
| 剪刀 | 收获产量 + 修枝清虫 | ×(1 + 0.08 × 等级) | ×1.4 | Lv5 |

**强化费用**（+1 → +5，园币）：`20 / 40 / 80 / 160 / 240` + `花汁 2 / 2 / 4 / 4 / 6` + `精炼花露 0 / 0 / 1 / 2 / 3`。

**设施（每地块一次性安装，永久）**：

| 设施 | 价格 | 效果 |
|---|---|---|
| 遮阳棚 | 80 | 该地块免疫干旱 |
| 保温棚 | 120 | 该地块免疫霜冻 + 冬季成长 ×1.25 |
| 堆肥箱 | 150 | 材料类 / 过剩果实转肥料，施肥成本 −40% |
| 支架 | 100 | 解除高作物对相邻低作物的**遮荫惩罚**（§6.1 的负项可被硬件对冲） |

- **不做耐久**：耐久是纯损耗设计，与「家庭陪伴」定位相悖；提升手段是**强化**而非更换。
- **倍率类工具维持 3 件，不加**：已有的三件（浇水 / 施肥 / 产量）刚好覆盖照料循环，再加就是无谓竞争，且每个新倍率都会稀释前面所有机制。
- **明确不做「自动浇水 / 滴灌系统」**：它会让「每天来看一眼、顺手浇一下」这个核心互动循环消失。玩家一旦不用管水，就不会打开页面。宁可让缺水有压力，也不要自动化。纯函数已保证「放着也会长」——那是**免打扰**，但**照料才有增益**。
- **设施与作物绑定解锁**（§3 阶段 3/6）：扩建是这些作物能种的前提，不是白送。

| 抗寒剂 | 薰衣草 ×1 | 全家 48h 免霜冻 |
| 驱虫剂 | 薄荷 ×2 | 清除该地块虫害（§8.2），家庭 24h 冷却 |

**增益总规则**：短效 buff 最多同时生效 **3 个**（先到期先失效），成长总乘数**硬顶 ×3.0**；永久增益只有园丁等级（+5%/级）、图鉴（+0.5%/种 + 套装 +3%/套）与里程碑四路，无第五种叠加源。

**排期设计的四条考虑**

1. **6 个空窗（25%）是有意的**：惊蛰 / 立夏 / 小满 / 处暑 / 寒露 / 小雪 无事件。节气每 15 天换一次，若 24 个全有效果，玩家会陷入「天天看日历」而忘了照料本身。空窗让节奏有起伏，也给「下一个节气有什么」的期待感。
2. **「露润」与既有机制同源**：§8.1 的昼夜温差（当日最高−最低 < 5℃ 则甜度 −10%）本来就是个**减益**。白露本就是「昼夜温差大、露水凝结」，把它绑成**旺季增益**就有了双向含义——玩家会为了赶在白露前种下某作物而调整时序。**春分 / 秋分昼夜平分，温差为 0，故增益失效**（天文事实，顺手做了一个「明明是旺季却没加成」的意外）。
3. **「休眠」只冻室外，室内免疫**：这是 §3「室内 = 保底区」承诺的兑现——冬天有一个明确的「该回室内了」的转折点，同时不惩罚只买了三盆窗台的新手。
4. **事件数量刻意保持在 10 类以内**：12 个节气复用同一事件（春耕×2、梅雨×2、盛夏×2、休眠×2、寒潮×2、丰收×2），玩家感受到的是「连续几天同一效果」，不是精确的边界日。

**实现**：`content/events.json`，每条 `{ code, name_key(中英), start_md, end_md, effects[], scope }`，一个纯函数 `currentTerm(LocalDate)` 查表命中；**跨年注意 1 月的两个节气在小寒/大寒，取模处理**。

**与天气正交**：天气来自真实气象（和风，日内变化），节气来自日历（15 天一换），两者各自生效、不互相覆盖，但**叠加时共享 ≤×1.5 的上限**（§14.3 口径），仍受总乘数 ×3.0 硬顶约束。

**i18n**：24 节气名中英皆有标准译法（立春 Start of Spring / 雨水 Rain Water / 惊蛰 Awakening of Insects …），直接用现成的，不必自造。

### 14.5 庭院陈列（摆件：情感价值 > 数值价值）

- 摆件由**花束 / 材料加工**而来（干花束 / 苔藓盆景 / 迷你风车），在「庭院」页**横向陈列**，不占地块。
- **主要价值是「我种的东西被做成了」**——家庭产品里这比数值值钱。所以**不做 buff 加成**：若给加成，它就变成第 N 个乘数，撞 ×3.0 硬顶并稀释前面所有机制。
- 摆件只提供**情绪反馈**：陈列完成度、家庭共同制作数、解锁纪念章。
- **排期放到 P4**，且明确标注为可砍项——它是纯留存向内容，不影响任何核心循环。

## 15. 家庭交互与成长日志

- **通知**：成员照料 / 收获 / 解锁阶段 / 烹饪时经 `NotificationService` 通知其余成员（type=`plant`）；「浇水」这类高频动作在多地块 +12h 冷却后频次已自然下降。
- **寄语**：照料 / 收获附一句 ≤200 字寄语进日志，成为家庭共享内容（沿用 V1）。
- **日志**：`garden_log`（只追加），action 扩展为 `PLANT / WATER / SUN / MIST / FERTILIZE / HARVEST / SELL / COOK / CRAFT / UPGRADE / FACILITY / VENUE_UNLOCK / PRUNE / CROSS`；新增 `crop_code` + `variant` 列。
- ⚠ **图鉴另存 `garden_codex`**：若图鉴靠扫日志的 distinct `crop_code`，日志 180 天清理后图鉴会归零。codex 一家最多 86 行，永不删除（§16.4 要点 3）。
- 园丁等级、图鉴、集市进度均从日志 + 仓库**推导**，不另建进度表。
- **周挑战（零新系统）**：**复用现有 `family_task` 任务悬赏表**——花园周目标只是任务的一类目标类型（`本周收满 3 块地` / `本周只用花箱种满一轮` / `本周零霜冻收成`），目标达成按 `family_task.reward_points` 发积分。不建挑战系统、不建周榜表。
- **节气事件提示**：进入 / 离开事件时各发一条家庭通知（type=`plant`），让「为什么今天收益翻倍」有解释，不做暗改。

### 15.1 家庭成员分工（让「全家一起」不只等于共享仓库）

> 「合种共同培育」的体现不是资源共享，而是**人的差异**。V1 里所有成员操作完全等效，妈妈和孩子没有任何区别——这是主题最未被利用的地方。

**一条原则先定死：专精效果只在本人执行该类动作时生效。** 若做成常驻全家加成，一个人专精全家受益，分工就退化成「选一个词全家用」，机制即失效。

**五个专精领域**（互不重叠，各自对应一组动作）：

| 领域 | 覆盖动作 | 专精效果（本人执行时） |
|---|---|---|
| **育苗 SOWING** | 播种 / 扦插 / 杂交 | 种子价 −20% |
| **照料 CARE** | 浇水 / 晒太阳 / 施肥 / 补水 | 照料成长加成 +15% |
| **烹饪 COOK** | 制作食谱 / 消耗品 | buff 效果 +10%、时长 +6h |
| **工艺 CRAFT** | 材料加工 / 工具强化 | 材料产出 +1、强化费 −25% |
| **收获 HARVEST** | 收获 | 产量 +10%、保底计数 +1 |

**协作加成只留一条规则**（不写五条配对表）：当日**两名专精领域不同**的成员都动过手 → 全家当天成长 +5%（可叠加至 2 人，+5% / +10%）。这是唯一奖励「分工」的机制，也是唯一有真正社交含义的加成。

**认领规则**：

| 规则 | 值 | 理由 |
|---|---|---|
| 初始名额 | 1 个 | 先试一个方向 |
| 第 2 个名额 | 该领域累计操作 30 次后解锁 | 用行动换，不用积分买 |
| 改换 | 冷却 7 天 | 允许试错，不锁死 |
| 解锁判定 | 从日志按 action 分类**计数推导**，不落库 | 沿用「推导不落库」原则 |

**边界**（不写清楚一定出 bug）：

| 情况 | 处理 |
|---|---|
| 独居家庭（1 人） | 专精全额生效，协作不触发；**不做补偿加成** |
| GUEST 访客 | 最多认领 `CARE` 一个领域（仅轻动作） |
| OPS 账号 | 不适用（不属任何家庭） |
| 同领域两人 | **不算协作**，防刷 |
| 代他人操作 | 从 `player_uid` 取，不触发对方专精 |
| 跨家庭 | `family_id` 隔离，与其他模块一致 |

**复用既有设施**：`sys_user_role`（roleCode）+ `sys_user`（nickname/avatar）+ `family_user_label`（身份标签）+ `selectMembersByFamily` 现成成员列表，**均不新建、不改动**。⚠ 不把专精绑到 `sys_user_role`——那是权限体系，「只有 OWNER 能烹饪」是错的，孩子也能做饭。

**前端呈现**：成员头像行 = 头像 + 1~2 个专精小图标 + 今日是否动过手（亮点圆点）；照料按钮旁提示「本次含 XX 的专精加成」——**增益必须可见**，否则玩家感觉不到自己选对了。

**伦理约束**（家庭产品特有）：①专精**无强弱之分**（五域加成幅度刻意接近），不设排名、不显示「谁贡献最多」；②不制造家庭内部隐性分工压力，尤其避免孩子因数值低而更挫败。

### 15.2 日志保留期与数据量（必须在 P1 落地前定）

> V1 每天约 10 行；V2 是 **36 块地 × 12h 冷却 × 2 动作 ≈ 144 行/天/家庭**。一家 5 口、100 个家庭 → **每年 500 万行**。现有 `idx_family_created` 索引够用，但等级 / 图鉴全靠它 `COUNT` 推导——**表一大，每次打开页面都要扫一遍**，这才是真问题。

**分两级处理：热度数据落快照，历史日志定期清。**

| 手段 | 内容 | 为什么 |
|---|---|---|
| **计数快照** | 新增 `garden_stat(family_id, stat_date)`：当日照料数 / 收获数 / 园币收入 / 兑换积分数 | 等级 / 图鉴 / 周挑战改读快照，**不再扫 log**；快照本身是「每日一行」，一年 365 行 |
| **图鉴独立表** | 新增 `garden_codex(family_id, crop_code)`，永不删除 | 日志清理不能让图鉴归零（§15） |
| **保留期清理** | `garden_log` 保留 **180 天**，超期行删除 | 家庭回忆只需半年（「去年夏天我们种了什么」仍在范围内）；再久是别人的记忆 |
| **清理时机** | 复用现有定时任务位：`RecycleService.autoCleanExpired()` 每日 03:00 的模式，新增 `@Scheduled(cron = "0 30 3 * * ?")` | 与回收站 7 天清理同批跑，不新增部署配置 |
| **删除方式** | 自定义 XML `DELETE ... WHERE created_at < ? LIMIT ?`（**分批**） | ⚠ 项目规则：物理删必须走自定义 XML（MP `deleteById` 实为 UPDATE）；一次删太多会长时间持锁，按 1000 行一批循环 |

**必须避开的三件事**：
- **不要把 log 当审计表**——它只是游戏行为流水，不是合规记录，不进备份的必保范围。
- **不要用 log 推导「累计总量」类指标**（如「家庭一共照料过多少次」）——一旦清理就永久失真，这类数据只能从快照累加。
- **不要跳过快照直接清 log**——那样等级和图鉴会跟着一起归零。

**归档 vs 清理**：不做归档表。花园日志不涉及「找回」，且归档等于把 400 万行换个地方存，白费。

**容量兜底**：单家庭日志上限（建议 5000 行，超出时优先删最旧的照料类行、保留收获与首次收获行）——防「脚本刷日志」把单家庭撑爆。

### 15.3 拍照与晒图（花园唯一的情绪出口）

> **为什么是「唯一」**：相册、日记、博客都有产出，花园种了半年却**没有任何东西能带出游戏**——这是当前最大的洞。而且 ihomy 已有完整相册体系，花园是**唯一还没产出视觉内容的功能**。

**生成：canvas 手绘，零新依赖**

- 客户端是 Cocos，截图走**引擎自己的渲染管线**：Web 构建用 `game.canvas.toDataURL('image/jpeg')`（需在工程设置里开启 `preserveDrawingBuffer`），native 构建用 `Camera` + `RenderTexture` 截帧再读回像素——两条路都不碰 DOM。
- **不引 `html2canvas` / `dom-to-image` 这类 DOM 抓取库**：Cocos 的画面根本不在 DOM 里，它们抓不到；而且我们要的是干净的游戏画面，不是连弹窗一起抓。
- **契约依赖 §18.1 那层不变的 props**：`crop_code / stage / variant`。所以这条路跟「未来换 AI 图」是同一个前提——**换图不会让晒图功能失效**（只是序列化换成 `<img>` 绘制）。

**内容**：一张卡片 = 场域背景 + 地块网格 + 当前作物状态 + 一行文案（季节 / 节气 / 「今年第一茬番茄」这类自动生成的话）。**不渲染数值面板**——晒图是给家里人看的，不是给攻略站看的。

**落地**：走现有 `FileService` 上传，`visibility=FAMILY` 默认，**可选**指定相册（`content_photo.album_id`）。

| 项 | 处理 |
|---|---|
| 入口 | 场域页「拍照」按钮 + 收获成功弹层的「晒一晒」 |
| 隐私 | 默认家庭可见；**不给一键公开**，花园内容没有公开的价值（相册的 PUBLIC 是图片本身的属性，不是花园的） |
| 去重 | 同一天同一场域重复拍照，提示「今天已经拍过」——**让它变日常的小仪式，而不是相册垃圾制造机** |
| 数值 | **零**。不给积分、不给园币、不给图鉴加成（否则晒图会变成刷图） |

> **⚠ 一条边界**：晒图**不接积分**。ihomy 的积分来自内容创作（博客 10 / 日记 8 / 照片 2），若花园晒图发积分，就等于给一条「稳定产出积分」的旁路——§12 开头警告的就是这件事。

### 15.4 成就系统（叙事性，零数值零新表）

> 图鉴管「收集了什么」，里程碑管「玩了多久」，成就管**发生过的故事**——「第一茬番茄」「全家四口都动过手」「单日十连收」。三者互不重叠，也互不给数值。

**三条边界先定死**（不写清楚必返工）：

1. **零数值**：成就**不给任何加成**（成长 / 产量 / 园币 / 积分都不给）。理由同 §14.5——每加一个加成就是第 N 个乘数，撞 §14.3 的 ×3.0 硬顶并稀释前面所有机制；且成就一旦带数值，家庭产品里立刻长出「优先刷成就」的功利路径，叙事就死了。
2. **零新表零新公式**：已获得成就存 `garden_world.settings.achievements`，值为 JSON `{code: 获得时间戳}`——沿用 §18.2 `tutorial_done` 同一模式。⚠ **不要存 `sys_parameter`**：该表是全局表（无 `family_id`）且 `value` 仅 `VARCHAR(500)`，22 条成就必然溢出（§25.4 勘误）。判定条件全部是**对已有数据的纯函数读取**（快照 / 图鉴 / 成员表 / 地块表 / 本次动作参数），不新增运行时概念（§22 复杂度红线）。
3. **不做排行不做对比**：不显示「谁成就最多」、无家庭间榜、无完成度百分比排名。§15.1 伦理约束同源——成就一旦可比较，家庭内部立刻出现隐性分工压力。

**触发**：写动作完成后（收获 / 解锁 / 变体 roll / 烹饪 / 卖出），由该动作的 Service 顺带判定**与该动作相关的成就组**；JSON 里已有码的条目直接跳过。**不做全量扫描、不做定时任务**——判定成本必须贴在本来就发生的那次写上。

**条目**（起步约 22 条，全配置在 `content/achievements.json`）：

| 组 | 条目 | 判定读取（全部是已有数据） |
|---|---|---|
| **开端** | 第一茬（文案按作物生成：「第一茬番茄」） · 首次卖出 · 首次变体 · 首次烹饪 | 本次动作参数 + codex 新行 |
| **家庭** | 全家 N 人都种过 · 每人都收获过 · 两人同日动手（协作加成的叙事版） | `member.last_active_date / specialties` + 当日快照 |
| **坚持** | 连续 7 / 30 天有人照料 · 单日收获 ≥10 · 一个场域满编 · 休眠期仍收获 | `stat` 快照连读 + `plot` 当前态 + 当前节气 |
| **收藏** | 图鉴过半 · 集齐一种作物的全部变体 · 21 食谱做一半 | `codex` / 已解锁配方集 |

**边界情况**：

| 情况 | 处理 |
|---|---|
| 判定读取依赖日志 | **禁止**——日志 180 天清理会让判定失真（§15.2 同一课）；只读快照 / codex / member / plot |
| 老家庭补发 | 上线时跑一次补判定（读现有快照与图鉴，已达标的成就码一次性写入），不逐条补发通知 |
| 成就条目删除 | 配置里删条目 = 墙上不再显示，已写入的 JSON 码无害残留；**不迁移不清理** |
| 家庭解绑 / 成员退出 | 成就是家庭级的，随 family_id 走，与成员无关 |
| GUEST | 可获得「开端」组（他也在照料）；「家庭」组按实际动手成员数计 |

**前端**：图鉴页第二分区「成就墙」——已获得显示叙事名 + 获得日期（「2026-10 · 第一茬番茄」），未获得显示灰色剪影 + 一句**目标文案**。**显示目标、不显示进度条**：知道要什么，但不焦虑「还差 3 次」——进度条会把故事变回任务。获得时经 `NotificationService`（type=`plant`）推一条家庭通知，文案是叙事句不是系统句。

**i18n**：`garden.ach.*` 命名空间，中英键对齐；「第一茬 {作物}」这类模板句用插值，不为 86 种作物各写一条。

**扩展**：加成就 = `content/achievements.json` 加一行（code / 组 / 目标文案 / 阈值）+ i18n 两键；判定按组复用（四个组 = 四个判定函数），**不随条目数量增长**（§20 要点 13）。

## 16. 数据模型（十一张表 + 仓库配置）

### 16.1 表命名规范（本仓）

> 用户诉求原文（ihomy 侧多游戏场景）：「花园是游戏，开一个 `game_` 前缀，再以游戏名（简称）为词缀，再以模块为词缀……有的游戏是导入的放进 `game_info`，有的游戏是自己研发的，就单独词缀，而且小游戏页面里要展示所有游戏，那么所有游戏都要放到 `game_info` 里」。

**游戏名：家圃时光 · Home Garden Moments** —— *一圃藏四季，全家共耕耘 | Grow through seasons, together as a family*

**本仓命名（两段式）**：独立项目只有一个游戏，`games` 库表前缀直接用游戏名简称——`garden_<module>_<entity>`，不需要 ihomy 多游戏仓库的 `game_` 域前缀。ihomy 侧三段式 `game_<game_code>_*` 与 `game_info` 注册表属**集成事项**（见 16.2 标注），本仓不涉及。

```
garden_<module>_<entity>                本仓通用
game_info                                ihomy 侧存量注册表(集成事项,见 16.2)
```

| 游戏 | 前缀 | 归属 |
|---|---|---|
| **家圃时光** 花园 | `garden_*` | **本仓**（`games` 库） |
| **宠物连连看** | `game_petlink_*` | ihomy 侧，逻辑写在 `GameInfoController` 内，**无独立表** |
| 导入的 swf/gba | `game_info` | ihomy 侧，家庭隔离，用户导入的文件 |

**模块层判据**（按基数，不按语义层级——每多一层都要能回答「为什么」）：

> **模块层只在满足任一条时才建立**：① 该模块 ≥3 张表；② 该模块是独立聚合根（有自己的生命周期）；③ 该模块下有独立子域。否则直接 `garden_<entity>`。

据此：`market` 只有 wallet + listing 两张表且同属一条买卖流程 → **不开 market 层**；`member` 将来会挂进度 / 徽章 → **开 member 层**（现为 `garden_member`，只有 1 张表，是为将来预留）。

### 16.2 `game_info` 改造为全局注册表（ihomy 侧集成事项，本仓不涉及）

> **本节属 ihomy 仓**：`game_info` 是 ihomy 存量表，独立项目自身无此表。ihomy 游戏库页接入本游戏时按此执行；本仓只管 `garden_*` 业务表。

现状是「家庭导入的游戏文件清单」（`family_id` / `user_id` / `file_url` 均 NOT NULL）。既然小游戏页要展示**所有**游戏，它必须同时承载内置自研游戏：

| 字段 | 现状 | 改造后 | 说明 |
|---|---|---|---|
| `family_id` | NOT NULL | **可空** | 内置自研游戏为 `NULL` |
| `user_id` | NOT NULL | **可空** | 同上 |
| `file_url` | NOT NULL | **可空** | 自研游戏无文件 |
| `game_code` | — | **新增 VARCHAR(30)** | 稳定标识：`garden` / `petlink`；导入游戏为 `NULL` |
| `entry_path` | — | **新增 VARCHAR(100)** | 自研游戏入口 `/tools/garden`；导入游戏为 `NULL` |
| `type` | `SWF/GBA` | 扩枚举 | **`NATIVE`**(自研) / `H5` / `SWF` / `GBA` |
| `builtin` | — | **新增 TINYINT** | 1 = 内置不可删，0 = 家庭导入 |
| `sort_order` | — | **新增 INT** | 列表排序，内置固定在前 |
| `icon` | — | **新增 VARCHAR(200)** | 图标 / 封面 |

**判定口径**（不靠猜，靠是否为空）：内置自研 = `game_code` 非空且 `family_id` 为空；家庭导入 = `family_id` 非空且 `file_url` 非空。

**索引**：现有 `idx_family_created(family_id, deleted, created_at)` 服务不了全局列表，补 `idx_builtin_sort(builtin, status, sort_order, id)`。

**关键分界**：注册表只存**元数据**（长什么样、点去哪），业务数据一律在 `game_<code>_*`。注册表里永远不会有「第几株植物」这种字段，否则游戏一多这张表就废了。

**好处**：`Games.vue` 现在是「花园和连连看两个硬编码卡片 + `game_info` 动态列表」拼出来的，改成读 `game_info` 后**加游戏 = 插一行，不碰任何组件**。

**与 `sys_home_module` 的分工**：后者管「要不要在首页 / 侧栏露脸」，前者管「游戏库页里有哪些」，两者用同一个 `game_code` 关联，**不合并**（合并会让首页排序规则污染游戏库）。

### 16.3 落库 vs 推导：先划清才知道每张表为什么存在

| 落库（状态） | 推导（不落库，读时算） |
|---|---|
| 地块种了什么、什么时候种的 | 生长阶段、进度、成熟度 |
| 上次浇水 / 施肥 / 补水时刻 | 营养等级、枯萎判定 |
| 仓库有什么、多少 | 仓库容量占用 |
| 工具等级、buff、专精、园币 | **园丁等级** |
| 挂牌、日快照、图鉴、日志 | 季节倍率、间作与重茬修正、气温适配、变体 |

**推导列全部无存储**——所以改公式不需要数据迁移。

**静态内容进仓库 `content/*.json`**：

| 内容 | 去处 | 例 |
|---|---|---|
| 静态内容 / 配置 | 仓库文件 `content/` | 作物、变体池、食谱、杂交亲本表、场域网格、伴生表、24 节气事件、`sprite_param` |
| 玩家状态 | 数据库 | 见下表十一张 |
| 游戏逻辑 | `core` 纯函数包 | 成长公式、季节判定、roll、保底 |

**理由**（不单独立项也成立）：**客户端渲染同样需要这份数据**（作物名、精灵参数、季节条、变体池）。放 DB 就要给客户端开配置接口 + 缓存，而客户端仍会抄一份 → 等于漂移重来。进 `content/` 后由客户端按 `JsonAsset` 加载（Cocos 侧路径与同步规则见 `CocosCreator资源管理规范.md` §2.5），加作物是「改一行 JSON + git diff」，CI 用 `JSON.parse` + 单测遍历即可校验。

**配置双消费**：`content/*.json` 是唯一真相源，git 管；客户端从 `resources/content/` 加载（构建期由仓库根 `content/` 拷贝而来，见 `CocosCreator资源管理规范.md` §2.5），Java 侧由构建期复制进自己的 `resources/content/` 后加载校验（Java 只需价签 / 阶段 / 解锁等级这个最小子集）。两侧读同一份文件，不会漂移。

**十二个设计要点**（每条都是「不写清楚实现时必返工」的那种）

1. **场域解锁表不存在**：「已解锁场域」= 「该场域有 plot 行」，地块行本身就是记录，解锁价在 `content/venues.json`。少一张表，少一处双写。
2. **`member` 合并了专精表**：原本一人两行（`member_specialty`），改成 `specialties JSON` 一行；顺手放 `last_active_date`，**协作加成就不用扫日志判定「今天谁动过手」**。
3. **图鉴独立成表且与日志解耦**：这是 §15.2 的直接后果——图鉴若靠扫 `garden_log` 的 distinct `crop_code`，日志一清空图鉴就归零。`codex` 一家最多 86 行，永不删除。
4. **这十一张表都不需要 `deleted` 软删**：项目的软删是给照片 / 相册 / 视频 / 图书做回收站用的。花园是娱乐数据，误删可以重种，**加 `deleted` 只会让每个查询多一个恒定条件**。物理删走自定义 XML 分批（项目规则：MP 的 `deleteById` 实为 UPDATE）。唯一待定的是**世界级删除**（`garden_world` 整行），验收前必须定（§29.4）。
5. **`item_name` 快照在 listing 上**：挂牌时把名字冻住——否则以后改了作物名，历史挂单会显示出错的名字。
6. **`soil_type` 仅空地时可改**：这就是「花盆数量 / 耕地数量」的分配决策（后院 6 块地，自己定几块花盆几块耕地）。**种上了就不能改**，否则能用地块属性反复横跳。
7. **有 `ON UPDATE` 的表一律用 `LambdaUpdateWrapper`**：项目规范 11 —— MP 的 `updateById` 会把实体里的旧 `updated_at` 一起写回，抑制自动更新。
8. **`qty = 0` 即删除该行**：仓库不存 0 数量行，容量 `SUM(qty)` 才有意义。
9. **`wallet` 里没有积分列**：积分余额仍在 `PointsService`，兑换是单向写（园币 −N、积分 +M），事务 + 条件 UPDATE 保证原子。
10. **`stats` 里没有等级 / 图鉴列**：等级从 `stat` + `codex` 推导，不落库；快照只存**原始计数**，便于按任意口径重算。
11. **`garden_world` 取代了 `sys_parameter` 的家庭级 key**（§25.4）：`time_ratio` / `daily_points_cap` / `tutorial_done` / `achievements` / `warned_date` 全部进 `settings JSON`。⚠ 勘误——实测 ihomy 的 `sys_parameter` 是**全局表**（无 `family_id` 列），且 `value` 只有 `VARCHAR(500)`，22 条成就的 JSON 必然溢出；改存 JSON 列后顺带让**设置随存档走**，三端一致。
12. **六处用户引用列改 `player_uid`，绑定关系只存一处**：`garden_wallet.player_uid` / `garden_member.player_uid` / `garden_listing.seller_uid` / `garden_log.actor_uid` / `garden_plot.created_by` / `garden_buff.created_by`；`sys_user_id` **只加在 `garden_member` 上**。这样「同一份存档在三端跑」不需要任何 id 重映射（§25.2）——这是「数据可互通」在数据层的全部代价。

### 17.1 错误码与幂等约定（不写必返工）

**复用现有 `ResultCode`**：`OK=0` / `BAD_REQUEST` / `NOT_FOUND` / 权限 403 / 积分不足 1008（沿用 V1）。花园**不新增 ResultCode 枚举**。

| 场景 | HTTP | ResultCode | 前端文案要点 |
|---|---|---|---|
| 园币不足 | 200 | `INSUFFICIENT_POINTS`(1008) | 「还差 N 园币」——**必须带差额** |
| 仓库已满 | **409** | `BAD_REQUEST` | 「仓库满了，先卖些或吃些」+ 高亮仓库抽屉 |
| 冷却中 | **409** | `BAD_REQUEST` | 「这块地 X 小时后可再浇水」——**必须带剩余秒数**，前端据此置灰按钮倒计时 |
| 未成熟 | **409** | `BAD_REQUEST` | 「还要长 X」+ 进度条 |
| 非解锁地块 / 跨家庭地块 | **404** | `NOT_FOUND` | 不泄露存在性（沿用项目口径：跨家庭一律 404） |
| 阶段等级不足 | **403** | `FORBIDDEN` | 「园丁 LvN 解锁」+ 差几级 |
| 天气数据缺失 | 200 | `OK` | **不报错**：按季节默认均温继续算（§8.1），页面天气位显示「暂无」 |
| 场域非对应土壤 | 400 | `BAD_REQUEST` | 「后院这块是耕地，不能种花盆作物」 |

**幂等约定**（V1 只有冷却防刷，V2 涉及钱与货，必须更严）：

| 动作 | 幂等策略 |
|---|---|
| 浇水 / 晒太阳 / 施肥 / 补水 / 通风 | **条件 UPDATE**：`WHERE last_watered_at IS NULL OR last_watered_at < now - 12h`，影响 0 行即 409。不靠「先查后写」 |
| 收获 | 条件 UPDATE 锁定地块：`WHERE crop_code = ? AND growth >= total`；同时 `INSERT` 仓库行。**收获与入仓必须同一事务** |
| 卖出 / 挂单成交 | 条件扣减 `WHERE qty >= ?`，影响 0 行即 409；**园币与物品必须同一事务** |
| 园币兑换积分 | 事务 + `coins >= N` 条件扣；`PointsService` 写流水与扣币同事务；**每日上限判定先做**（否则并发下可超发） |
| 播种 | 地块 `WHERE crop_code IS NULL`，影响 0 行即 409 |
| **任意写动作（重试 / 重放 / 重连）** | `Idempotency-Key`(= `op_id`) + `garden_log.op_id` 唯一索引：重复即返回上次结果，**不重复扣款 / 不重复入仓**（§17） |

**统一原则**：**所有扣减都是条件 UPDATE + 0 行即失败**，不用「先 select 校验再 update」（后者在虚拟线程并发下必然出竞态）。这也是项目规范 11 的既有口径。

## 18. 客户端体验

- 页面沿用 `/tools/garden`（游戏库入口不变）：按**场域分区**纵向展示，每区一个标题条 + **地块网格**（§6.1 的行列布局）；未解锁场域显示占位卡（解锁条件 + 价格 + 「去解锁」按钮）。
- 地块卡：作物精灵（按阶段切换，资产策略见 §18.1）+ 进度条 + 土壤标签 + 设施角标 + 状态徽章（顺季 / 逆季 / 干旱 / 霜冻 / 待补水 / 徒长 / 灼叶 / 沤根 / 虫害 / 锦化）。
- 顶部状态条：等级与经验环、图鉴 x/86、当前季节与节气、天气与气温、生效 buff 芯片（倒计时）、成员头像行（专精图标 + 今日是否动过手）。
- 侧边抽屉：家庭仓库（分类堆叠 + 卖出 / 入厨 / 食用）与种子商店（按阶段分组、显示园币价与预期收益）。
- 图鉴页：**86 作物格子**（按 食 / 赏 / 材 分组），已收获点亮，显示各自季节条、土壤偏好、**该品种已收集的变体徽章**（白名单内收集，未收集显示灰色剪影，稀有变体带光环）。
- **变体渲染**：`sprite_param` 参数化组装——花型决定花瓣重复层数，叶纹叠一张通用遮罩贴图，花色走 Sprite 颜色 tint；变体稀有档在地块卡加一层柔光边框。**变体不逐作物出图**（§18.1 资源清单）。
- 30s 轮询对齐家庭最新进度；动作用条件 UPDATE 原子累加（沿用 V1）。
- **间作可视化（§6.1）**：① 播种弹窗**实时预览这一格的全部邻居效应**——正/负图标 + 百分比 + 一句「这里挨着薄荷园，会被抑制」；② 地块卡角标显示当前生效的间作图标。**看不见的机制等于没有机制**。

### 18.1 美术方案（Cocos 客户端；极简参数化资产，未来换 AI 图）

> **2026-10-13 改写**：客户端定为 **Cocos Creator 3.8**——原稿写的「Vue + SVG 零位图」已作废。本节保留与引擎无关的部分（**三层渲染契约 / 10 种形态 / 风格约束 / 实施顺序**），渲染手段换成 Cocos。

**从 V1 继承的底座**：V1 的 `PlantSprite.vue`（89 行）已证明「参数化画植物」可行——品种差异只是 4 个颜色，阶段差异只是 `stemTop / leaves / head` 三个数。V2 沿用同一思路，但落到 Cocos：**资产按「形状 × 参数」组装，不画 86×6 张图**。

**三层渲染契约**（硬要求：组件边界不能糊，否则未来换图要重写）

| 层 | 现在 | 未来换 AI 图 |
|---|---|---|
| 作物视图组件的公开接口 | `cropCode / stage / variant / wilted / size` | **完全不变** |
| 内部实现 | 10 种形态的参数化组装（几何或贴图叠加） | 换成一次 `loadSpriteFrame(cropSpritePath(code))` |
| `content/crops.json` | 多一份 `sprite_param` | 多一份 `asset` 路径 |

**为什么不用 emoji**：多色 emoji 无法可靠着色（`hue-rotate` 会把整张图搞脏），且**变体（重瓣 / 白边 / 斑叶）根本无法用 emoji 表达**。

**十种形态**（每个 ~10 行，一个作物最多 3 个基本形状；这部分是写几何代码，不是画画）：

| 形态 | 构成 | 适用 |
|---|---|---|
| `ERECT` 直立 | 茎 + 1~2 叶 + 头 | 向日葵 / 番茄 / 咖啡 |
| `CLIMB` 攀爬 | 支架线 + 缠绕茎 + 垂果 | 葡萄 / 豌豆 / 火龙果 |
| `MAT` 垫状 | 一团圆弧 | 苔藓 / 猫草 / 百里香 |
| `CRAWL` 匍匐 | 横向茎 + 低叶 + 落地果 | 南瓜 / 草莓 / 花生 |
| `FLOAT` 漂浮 | 圆叶 + 花 | 碗莲 / 铜钱草 / 泽泻 |
| `TRAP` 捕虫 | 夹状双瓣 | 捕蝇草 |
| `HANGING` 垂吊 | 悬垂链 + 串珠叶 | 绿萝 / 吊兰 / 鹿角蕨 |
| `ROSETTE` 莲座 | 放射状叶丛 | 多肉 / 仙人掌 / 凤梨 |
| `BUSH` 丛生 | 多分枝球形 | 薄荷 / 罗勒 / 栀子 |
| `TREE` 乔木 | 主干 + 树冠 | 芒果 / 咖啡 / 棕榈 |

> 扩到 **10 种**是为了容纳家居植物——**垂吊**（吊兰 / 绿萝）和**莲座**（多肉 / 虎皮兰）是家庭种植绕不开的两类。每个形态约 10 行，总共约 100 行代码，仍远小于画 86 张图。

**资源清单（本节与 `CocosCreator资源管理规范.md` 的接口）**：

| 资产 | 数量 | 命名 | 说明 |
|---|---|---|---|
| 作物成熟态 | 86 | `crop_<crop_code 小写>` | 每种 1 张；阶段差异靠缩放与参数插值 |
| 通用芽 | 1 | `crop_sprout` | 形态未分化前的阶段共用 |
| 变体遮罩 | 3 | `fx_variant_<叶纹>` | 白边 / 斑叶 / 白化，86 种复用 |
| 场域背景 | 6 | `bg_venue_<venue 小写>` | **唯一的新增美术资产** |

**场域背景是唯一的新增美术资产**（6 张）。它同时承担美术与**功能表达**：生态缸背景要一眼看出「不怕霜冻」，后院要能看出「会刮风下霜」，大棚要看出「季节免疫但怕温度」。建议把风格风险主要压在背景上，作物本体保持极简——游戏主体是网格，背景才有展示空间。

**风格约束**（现在定死，未来换图才不跑偏）：
- **无渐变**（渐变立刻拉低扁平风质感）
- 统一描边 `rgba(0,0,0,.12)` / 1px
- 柔和投影走同一套参数，不逐图烘焙
- 配色用同一份色板变量，跟随暖居 / 光尘两轴，深色模式自动跟随
- 图标走线性风格、统一描边（原稿写 Element Plus `el-icon`，换引擎后**图标来源待重定**）

**未来换图的图片成本**（这决定现在怎么画）：

| 方案 | 张数 | 判定 |
|---|---|---|
| 作物 × 6 阶段全画 | **516 张** | ❌ 不现实，且风格漂移风险极高 |
| **只画成熟态，阶段用缩放 / 裁切** | **86 张** | ✅ 推荐，再加 1 张通用「芽」图 |
| 变体用后期叠加 | +3 张通用遮罩（白边 / 斑叶 / 白化） | 86 种复用 |

**结论**：现在画「可缩放的剪影」，未来每种作物只需 1 张成熟态图——与上面资源清单的 86 张对上。阶段差异靠参数插值，所以现在的参数化结构天然就是未来的缩放规则——**现在这遍不会白画**。

**实施顺序**（反过来会返工）：
1. 先做 **6 张场域背景**，定死视觉语言（配色 / 描边 / 投影 / 透视）
2. 再把渲染器扩到 **10 种形态**，用 V1 的 3 个品种做回归
3. 最后填 **86 组 `sprite_param`**——纯数据工作，可边填边玩

> **待定（决定上面资源清单是否成立）**：作物本体用**贴图**还是用 Cocos 的 `Graphics` 组件**在引擎里画几何**。选贴图 → 按 86+1+3 张执行（`CocosCreator资源管理规范.md` 已按此建目录）；选 `Graphics` → 位图归零，但要在 Cocos 里重写 10 种形态的几何，作物贴图目录留空。同时图标来源需另定。

### 18.2 新手引导（不建教程系统）

> 复杂度陡坡是真实风险：86 作物 × 28 地块 × 6 场域 × Lv100 × 变体 × 市集 × 专精。**但不需要教程系统**——三招解决。

**① 渐进解锁本身就是引导**：Lv1 只有窗台 3 盆 + 阶段 1 的 8 种作物，且**只暴露 3 个动作**（浇水 / 晒太阳 / 收获）。施肥、市集、变体、加工、专精全部在玩家已熟悉基本循环之后才出现。复杂度天然分批曝光。

**② 首触引导（事件驱动，出现一次）**：每个触点只弹一次说明，之后永不出现。复用既有的弹窗 / 气泡预制体 + 一条「已展示」标记，**零新系统**。

| 触点 | 触发时机 | 教什么 |
|---|---|---|
| T0 | 首次进入花园 | 一句话：这是全家的花园，可以一起种 |
| T1 | 首次进入 | 播种（此时只显示阶段 1 的 8 种） |
| T2 | 首次浇水 | 浇水 + 12h 冷却提示 |
| T3 | 首次晒太阳 | 晴天晒太阳加成更大 |
| T4 | 首次成熟 | 收获 → 果实进**公共仓库** |
| T5 | 仓库首次满 5 件 | 市集：卖出换园币 |
| T6 | 园币首次 ≥ 200 | 提示可解锁下一阶段 |
| T7 | 解锁新场域 | 新场域说明卡（能做什么 / 怎么玩 / 预期收益） |
| T8 | 首次出现变体徽章 | 变体系统：同一种作物会长出不同样子 |
| T9 | 首次触发重茬 | 「这片地刚种过茄科，会减产，换一种」 |
| T10 | 首次出现异常状态 | 状态系统：会病不会死，照料能治 |
| T11 | 首次两人同日操作 | 协作加成：分工合作有加成 |
| T12 | Lv20 / 30 / … | 里程碑说明卡 |

**③ 解锁说明卡**：解锁新场域 / 新阶段时给一张可跳过的卡片，说明「新增了什么 + 怎么搭配已有内容」。

**存储**：`garden_world.settings.tutorial_done`，值是已完成触点的 JSON 数组。**不新建表**（原 `sys_parameter` 口径已废，§25.4）。

> **反模式**：不要做「关卡式教程 / 新手任务链 / 强制弹窗序列」——那是把复杂度从系统挪到内容，维护成本翻倍且必然被玩家跳过。首触式提示只在玩家**已经困惑的那一刻**出现。

## 20. 扩展性与后期改动点（合并 V1）

1. **改数值** → 只动 `PlantConst` 与 `content/*.json`，业务代码零改动。
2. **改公式** → 阶段 / 营养 / 等级 / 图鉴均为纯函数推导、不落库，改公式后历史植物立即按新规则解释，**无需数据迁移**。
3. **加作物** → `content/crops.json` 一行 + 一组 `sprite_param` + i18n 文案，零平衡成本（外观参数化，6 阶段由同一组参数插值）。
4. **加变体位点** → 在某作物的 `trait_pool` JSON 里加一个取值 + 一条 `variant_whitelist` 条目；渲染层已有通用叠层 / 遮罩 / 色相三种滤镜，通常**不需要写新代码**。
5. **加杂交配方** → `content/recipes.json` 加一行 `type=CROSS` + 亲本兼容表加一条；属性融合规则是一个纯函数，不随配方数量变化。
6. **加伴生对 / 科属** → `content/companions.json` 与 `crops.json` 的 `botanical_family` 各加一行；间作与重茬判定是两个纯函数，不随条目数量变化。
7. **加专精领域** → `specialties` 配置加一条 + 在动作分类表里把某类 action 归给它；效果是一行乘数，不进主公式。
8. **加作物形态** → `SPRITE_FORMS` 加一个形态枚举 + 写一个约 10 行的几何函数；已有形态的组合与调参都不动。**未来换位图时这一层被整体替换，props 契约不变**（§18.1）。
9. **加食谱 / 摆件** → `content/recipes.json` 加一行（`type=COOK` / `CRAFT` / `PRUNE` / `CROSS`）；材料链有 3 条**规则**覆盖全部材料作物，新增材类作物不必再写配方。
10. **加天气源 / 条件** → 复用 `WeatherService` 抽象，游戏层只消费归一化 condition，无感知（沿用 V1）。
11. **加积分事件** → `PointsRuleConst` 加规则键 + 家长规则表，缺行回退默认（沿用 V1）。
12. **内容沉淀** → 日志只追加，图鉴 / 统计 / 成就可随时叠加而不破坏历史。
13. **加成就** → `content/achievements.json` 加一行 + i18n 两键；判定按组复用四个纯函数，已获得码存 `garden_world.settings.achievements`（零新表），不随条目数量增长。

## 22. 风险与边界（合并 V1）

- **天气是采样不是历史**：事件判定只用「当前天气 + 地块状态」推导，不追溯历史天气、不引后台定时任务（沿用 V1）。
- **积分并发**：沿用 V1 取舍（同积分商城口径，低并发不强行加锁），仓库扣减用条件 UPDATE 原子防超扣（§17.1）。
- **通知噪声**：浇水类高频动作靠地块冷却自然降频；后续可加安静时段，当前只排除操作者本人（沿用 V1）。
- **数值平衡**：默认值为「有陪伴感但不肝」的起步值，按实际家庭使用数据再调（§12.3 的观测方案 + 调参入口）。
- **⚠ 作物扩容的内容质量风险**：200 种里若有大量凑数条目，玩家一眼看穿。**准入门槛**：每种必须有至少一条真实差异（季节 / 土壤偏好 / 价格档 / 一条特性），只有名字不同的不许进。
- **⚠ 变体池表滞后**：§5.3.2 目前只覆盖到 86 种的骨架，**P1 开工时必须逐条按植物学补齐**——不能靠现有表格右推（空气凤梨不该有花型位、棕榈的叶纹只有全绿两种、咖啡树的变体是果实颜色）。
- **⚠ 科属表滞后**：§6.1 的科属对照需在 200 种时扩到 35+ 科，否则重茬机制失效（同科挤 30 种，玩家随便挑都不触发）。
- **复杂度红线**：本设计的复杂度只来自**配置表与乘积公式**，不引入新运行时概念（无新货币 / 无背包系统 / 无烹饪引擎 / 无后台任务）；任何后续玩法优先问「能否靠加配置行解决」。**§24–§30 的模式层是有意的例外，但它加的是「边界层」而不是「机制」**（端口 + 适配器 + 存档格式），核心玩法与数值一行不改；代价是**测试面扩大**，见下条。
- **⚠ 三端一致性是新的长期维护面**：同一个动作要在单人 / 房主 / 服务器三处给出同一结果。护栏有三层：① guard 判定只有一份（`garden-core` 纯函数）；② `content_version` 闸门挡住配置漂移；③ **golden 重放测试**——固定一份 op-log，在三种后端重放，断言状态哈希逐字节相同（§25.3）。**没有第 ③ 条，前两条都只是纸面保证。**
- **⚠ P2P 房主不可信**：不假装安全，而是把不可信性隔离在玩法层（不发积分、不给跨模块出口、不参与排名）；通往可信只有 §29.3 的结算网关一条路。
- **⚠ 单人存档无上限膨胀**：单人/桌面没有服务端容量约束，§15.2 的日志保留期必须同样生效，且**删日志前先写快照与图鉴**（顺序错了就是把等级与图鉴清零）。
- **⚠ 模式扩散的 UX 风险**：三种模式 + 能力开关会让同一页面出现多种形态。规定：**能力缺失时不渲染入口**（而不是置灰），并在 `/worlds` 标注每个世界的 `origin` 与「能否兑换积分」，避免玩家以为「我的园币能换积分」。

## 23. 落地约束（实现时必读）

- **结构变更双文件**：`schema.sql` 全量 + `migrations.sql` 幂等增量，两处同步，并按 CI 同路径做空库全量导入实测。
- **配置不进库**：`content/*.json` 由 git 管，不写 `schema.sql` / `migrations.sql` 种子段；Java 侧构建期复制进 `resources/content/`。因此**表数只算 11 张业务表**，内容变更不需要迁移。
- **V1 重构，不做兼容**（§16.5）：`family_plant` / `family_plant_log` 直接 `DROP` 重建为 `garden_plot` / `garden_log`；不写适配层、不保留旧接口。`DROP` 前一句 `INSERT ... SELECT` 把存量行搬进「窗台 slot 1」，别弄丢用户已养的植物。
- **表数口径（ihomy 侧）**：若表建在 ihomy 库 → 新增 **11** 张表 → 81 → **92**，同步 `AGENTS.md` / 需求 §6.2 / 部署指导表数（doc-drift 闸门会拦）；**现网仍是 81，AGENTS.md 不得提前改**。本仓表建在独立 `games` 库，不动 ihomy 表数。
- **表命名**：本仓新表一律 `garden_<module>_<entity>`（`games` 库；游戏域是顶层类别不挂在 `family_` 下），模块层判据见 §16.1。`game_info` 注册表改造是 **ihomy 侧集成事项**（§16.2），本仓不涉及。
- **⚠ 日志保留期必须在 P1 一起做**（§15.2）：`garden_log` 的 `DELETE` 必须是**自定义 XML 分批删除**（项目规则：物理删走自定义 SQL，MP 的 `delete` 实为 UPDATE；一次删太多会长时间持锁），定时任务复用 `@Scheduled(cron = "0 30 3 * * ?")`（与回收站 03:00 同批，不新增部署配置）。`garden_stat` 快照、`garden_codex` 图鉴表与 log 清理**必须同批上线**——只清 log 不建它们会让等级与图鉴归零。
- **需求文档**：§4.13.1 花园小节改写为 V2 形态、§7 补新端点、§9.1 规划项在实现后移入「已完成」。
- **i18n**：作物 / 食谱 / 工具 / 场域 / buff / 节气 / **成员专精**文案统一 `garden.*` 命名空间，中英键对齐（`hardcoded-cjk.spec.js` 会扫模板硬编码）。节气名用现成标准英译，不自造；作物英文用通用名 + 拉丁学名。
- **权限**：沿用「登录即可 + 家庭隔离」，**不新增权限码**；写接口全量 `@OperationLog`。⚠ 专精**不绑 `sys_user_role`**（那是权限体系，「只有 OWNER 能烹饪」是错的）。
- **⚠ 园币不碰积分表**：园币余额在 `garden_wallet`，积分余额仍在 `family_points_record`（`PointsService` 按 `user_id` 求和，**不是 `sys_points`——该表在 ihomy 中不存在**，见 §30.2 勘误）。兑换是**单向写**（园币 −N、积分 +M），用事务 + 条件 UPDATE 保证原子；**不得**新增 `points → 园币` 的反向路径。
- **设置页入口**：新增「花园设置」（仅 OWNER 可见），读写 `garden_world.settings` 的 `time_ratio` / `daily_points_cap` 两个字段（**原 `sys_parameter` 口径已废**，该表全局且值上限 500 字符，见 §25.4）；AI 建议复用 `AiService`（新功能码 `GARDEN_BALANCE`），家庭级 AI 须家长先加模型再绑定。
- **美术是 P1 的阻塞项**，不是后期打磨；且顺序必须是「6 张场域背景 → 10 形态渲染器 → 填 86 组参数」，反了必返工。
- **视觉回归面在接口之外**：86 作物 × 6 阶段 × 变体三层是人工看图的活，CI 的 `doc-drift-check.sh` 只管结构，需另立一份渲染验收清单。
- **模块种子**：`sys_home_module` 的 `plant` 行（默认停用）改 code=`garden`，入口仍在游戏库；如需首页露出再单独开启。
- **⚠ 核心零平台依赖**：`garden-core` 只接受注入的数据（今日天气快照 / 气温 / `now` / 随机源），**不得 import 任何 ihomy 服务或 HTTP 客户端**。三端可跑全靠这一条（§24.3）。
- **⚠ 核心确定性**：禁 `Math.random` / 禁直接取 `now()` / 禁浮点比较（一律整数基点）。连带影响：`VARIANT_ROLL_SEED` 由「`plotId + harvestCount`」改为「**地块自然键 + 收获计数**」——自增 `plotId` 跨端不稳定，用它做种子会让同一块地的变体在两端不同（§25.1）。
- **⚠ 家庭级设置改存 `garden_world.settings`**：不再用 `sys_parameter`（全局表 + `VARCHAR(500)`，成就会溢出）；连带 `garden.warned_date` / `tutorial_done` / `achievements` 一并迁移（§25.4）。
- **⚠ 标识层改造六处 `user_id` → `player_uid`**（§16.4 要点 12），`sys_user_id` **只加在 `garden_member`**；任何新增表都不得再引入 `user_id` 列。
- **⚠ 存档导入必须净化**：时间戳全部钳制 `≤ imported_at`，`origin` 不可篡改（§29.2）。这是「数据可互通」与「经济不被刷爆」的分界线，**不是可选优化**。
- **⚠ 积分只在 `platform=IHOMY`**：非 ihomy 平台 `capabilities.points=false`，前端**不渲染**（不是置灰）兑换入口；P2P 在结算网关落地前同样无积分（§24.2、§29.3）。
- **⚠ 三端一致性要有可执行验收**：固定 op-log 在三种后端重放，断言状态哈希一致（golden 测试）；它与「美术验收清单」并列，属于**接口之外的验收面**（§22）。

## 24. 运行模式：一核三端

> 用户诉求原文：「设计单人玩法、多人 P2P 玩法，服务器玩法，保证数据可互通，保证如果连接的是 ihomy 服务器可以实现与 ihomy 的互联互通。」

**这条诉求的性质**：它不是「再加三个玩法」，而是**给已有的纯函数核心补一层边界**。§1 原则 1（推导不落库）与 §16.3（静态内容进 `content/*.json`）已经把游戏逻辑做成了「无 IO 的纯函数 + 配置」，只是**没写清它跑在哪、状态存哪、权威归谁**。三种模式就是这三个问题的三个答案。

### 24.1 三个术语先定死（否则「家庭」与「世界」必然混用）

| 术语 | 定义 | 三端要求 |
|---|---|---|
| **核心 `garden-core`** | 无 IO 的纯函数包：成长 / 季节 / 营养 / roll / 全部判定 + `content/*.json` | **同一份代码、同一份配置**（漂移用 `content_version` 闸门拦，§25.3） |
| **世界 World** | 一份存档的容器：地块 / 仓库 / 钱包 / 工具 / buff / 挂单 / 图鉴 / 快照 / 日志 / 成员 / 设置。**泛化了「家庭」** | 三端同一模型 |
| **成员 Member** | 世界内的玩家身份，`player_uid`（ULID）跨端稳定 | 三端同一标识 |
| **权威 Authority** | 有权判定「这次动作成不成立」的那一端；每个世界同时只有一个：`LOCAL` / `HOST` / `SERVER` | ★ 三者互斥 |

- **家庭是世界的一种（`kind=FAMILY`）**，不是唯一形态：P2P 串门用 `kind=COOP`，单机用 `kind=SOLO`。这样 §15 的家庭交互 / 专精协作 / 伦理约束**原样复用**，不需要为 P2P 另写一套社交规则。
- ⚠ **`world_id` ≠ 账号**：ihomy 登录态（JWT `familyId`）只是「服务器模式取世界」的**一个来源**，不是世界的定义。否则单人与 P2P 会被迫先注册——那是把 ihomy 变成前置依赖，不是「可互联」。

### 24.2 三端定义（一张表说清差别）

| | **S · 单人 Solo** | **P · 多人 P2P** | **C · 服务器 Server** |
|---|---|---|---|
| 权威 | `LOCAL`（本机） | `HOST`（房主） | `SERVER` |
| 核心跑在哪 | 客户端 | 房主（权威）+ 成员（乐观预测） | 服务端；客户端零权威 |
| 存档 | 本地（IndexedDB / 桌面文件） | 房主本地 + 每成员一份可接管副本 | 数据库（`games` 库） |
| 传输 | 无（函数调用） | WebRTC DataChannel | HTTPS + WebSocket |
| 身份 | 本地 `player_uid`，可选绑定 ihomy | 房间内 `player_uid` / 票据 | ihomy JWT 或 standalone 令牌 |
| 世界类型 | `SOLO` | `COOP`（也可 `FAMILY`） | `FAMILY`（ihomy）/ 任意（standalone） |
| 网络 | 零要求 | 房主与成员连通即可 | 必须在线 |
| **积分出口** | **无** | **无**（结算网关落地前，§29.3） | **有**（仅 `platform=IHOMY`，§12 汇率与封顶） |
| ihomy 能力 | 无（`LocalPlatform` 替身） | 无（替身；信令可借道 ihomy） | 全量（§30） |
| 定位 | 离线 / Steam / 断网续玩 | 亲友邻里串门、合种 | 家庭常态 + 积分与内容生态 |

**三条硬规定**（已并入 §1 原则 9–11，这里给「落到模式层的含义」）：

| 规定 | 含义 |
|---|---|
| **积分只在 `C + IHOMY` 产出** | S / P 的园币是「本地分数」，UI 必须写明「不可兑换积分」——否则 §12.1 的币种隔离在模式层被打穿 |
| **权威不可并存** | 一个世界同一时刻只有一个权威；换模式 = 换权威 = 一次**显式迁移**（§29），不是「随时双向同步」 |
| **核心必须确定性** | 三端重放同一 op-log 必须得到逐字节相同的状态（§25.3 验收口径）；这是 P2P 与结算网关成立的前提 |

### 24.3 分层：谁调谁

```text
  客户端（同一份 Cocos 构建 / 同一套 i18n · 按 /garden/meta 的 capabilities 渲染）
        │
        │ GardenPort：读状态投影 / 提意图 / 订阅变更 —— 唯一抽象
   ┌────┼─────────────────────────────┬──────────────────────────────┐
   ▼                                  ▼                              ▼
 SoloPort（函数调用）            RtcPort（op-log 广播）         HttpPort（REST + WS）
   └────────────────┬───────────────┴──────────────────────────────┘
                    ▼
        ┌───────────────────────┐          ┌───────────────────────────┐
        │ garden-core 纯函数核心 │◀──配置───│ content/*.json（唯一真相源）│
        │ 无 IO · 确定性 · 可重放 │          └───────────────────────────┘
        └───────────────────────┘
                    ▲
                    │ GardenPlatform：世界之外的能力（身份/天气/通知/积分/冰箱/照片/注册表）
        ┌───────────┴────┐
        ▼                ▼
 IhomyPlatform      LocalPlatform（季节默认值 / 本地食材仓 / 应用内通知 / 无积分）
 （真实 ihomy 接口）
```

- **`GardenPort` 是唯一抽象**（三端各一个实现）⇒ 前端只写一遍。新增一种模式 = 加一个 Port 实现，不是加一套页面。
- **`GardenPlatform` 是「世界之外的世界」**：ihomy 是它的一个 provider，不是唯一。**加一项 ihomy 能力 = 加一个 provider 方法 + 一个 `LocalPlatform` 替身**，核心不动。
- ⚠ **核心不得 import 平台能力**：`garden-core` 只接受注入的「今日天气快照 / 今日气温 / `now` / 随机源」等**数据**，绝不调用 `WeatherService`。这是三端可跑的机械保证，也是纯函数单测能跑起来的前提（§23 落地约束）。

## 25. 规范存档模型（GardenSave v1）与全局标识

### 25.1 红利：现有十张表的唯一键本来就是「游戏自然键」

| 表 | 现在的唯一键 | 是否自然键 |
|---|---|---|
| `garden_plot` | `(family_id, venue, slot_no)` | ✅ |
| `garden_inventory` | `(family_id, item_code)` | ✅ |
| `garden_wallet` | `(family_id, player_uid)` | ✅ |
| `garden_tool` | `(family_id, tool_code)` | ✅ |
| `garden_member` | `(family_id, player_uid)` | ✅ |
| `garden_codex` | `(family_id, crop_code)` | ✅ |
| `garden_stat` | `(family_id, stat_date)` | ✅ |
| `garden_buff` / `garden_listing` / `garden_log` | 仅自增 `id` | ❌ 三张例外，且都是**暂态或追加型** |

**七张表的唯一键里只有 `family_id` 是世界作用域的**，其余全是游戏自然键（场域+序号 / 物品码 / 工具码 / 作物码 / 日期 / 成员标识）。三张例外里，buff 与 listing 本来就是暂态（72h / 48h 到期），log 是追加流水。

**结论**：互通**不需要新数据模型**，只需要两件事——① 把 `family_id` 那一列抽象成「世界作用域 ID」；② 给追加型流水补一个跨端稳定标识（`op_id`）。这是最小改造，且**不动任何一个索引、不动 §17.1 的条件 UPDATE 口径**。

### 25.2 标识层改造（四处，其余 DDL 一字不动）

| 项 | 现状 | 改造 | 为什么 |
|---|---|---|---|
| 世界作用域 | 十张表的 `family_id BIGINT` | **列名与类型不变**，语义扩为「世界作用域 ID」，由 `garden_world.id` 供给；ihomy 模式下 `garden_world.id == family_id`（恒等映射） | 不动索引 / 不动既有 SQL / ihomy 侧语义不变 |
| 玩家标识 | `garden_wallet.user_id`、`garden_member.user_id`、`garden_listing.seller_id`、`garden_log.user_id`、`garden_plot.created_by`、`garden_buff.created_by`（**共六处**） | 改 `player_uid CHAR(26)`（`seller_uid` / `created_by` 同改 `CHAR(26)`）；**只在 `garden_member` 上**加可选 `sys_user_id BIGINT` 绑定列 | `user_id` 是 ihomy 内部号，Solo / P2P 里不存在；绑定关系只存一处，不散落六张表 |
| 追加流水 | `garden_log` 仅自增 `id` | 补 `op_id CHAR(26)` 唯一 + `lamport` + `device_id` + `origin` | 追加型流水必须能去重，否则重复导入 / 重放会翻倍 |
| 世界元数据 | 无（散落在 `sys_parameter` 的家庭级 key，见 25.4） | **新增 `garden_world`（第 11 张表）** | 世界要可寻址、可追溯、可携带设置 |

- ⚠ **`player_uid` 与 `sys_user_id` 单向绑定、永不互相覆盖**：前者是花园内部标识（三端都有），后者是外部引用（只有 ihomy 模式有）。§15.1 里「从 `user_id` 取」读的即 `player_uid`。
- 改造后 **`user_id` 这个列名在花园表里彻底消失**——这是刻意的：留有 `user_id` 就一定会有人在那里塞 ihomy 的号，三端可移植性当场破功。

### 25.3 存档头与两道版本闸门

```json
{ "save_version": "1.0",
  "content_version": "<sha256(sorted content/*.json)>",
  "world": { "world_id": "01J...", "kind": "FAMILY", "origin": "IHOMY",
             "authority": "SERVER", "external_ref": "ihomy:family:123", "host_epoch": 0 },
  "exported_at": "...", "exported_from": "SERVER", "checksum": "<sha256(payload)>",
  "payload": { "plots": [], "inventory": [], "wallet": [], "tools": [], "buffs": [],
               "listings": [], "codex": [], "stat": [], "members": [], "log": [],
               "settings": {} } }
```

- **`payload` 的字段名 = 表列名**（十张表的机械投影；`family_id` 不出现——作用域由世界决定）⇒「服务器导出一份存档」就是十张表的 `SELECT`，**零映射代码**，也不会随代码演化而漂移。
- **两道闸门**：`save_version` 管结构（不同则走代码迁移），`content_version` 管数值解释（不同则走 `content/migrations/*.json` 数据迁移）；**两道都对才导入**，否则输出差异清单并拒绝——**不猜、不半读取**。
- **`content_version` 是 P2P 的硬闸门**：房主与加入者不一致即拒绝加入。因为「A 的番茄 3 天熟、B 的 5 天熟」会让两端状态必然分歧。
- `checksum` 只防传输损坏 / 误传，**不承担防作弊**（防作弊在 §29）。
- ⚠ **确定性口径**：核心的 roll 与判定必须只依赖「状态 + 注入的 `now` + `content_version`」。`VARIANT_ROLL_SEED` 原为 `plotId + harvestCount`，因自增 `plotId` 跨端不稳定，改为**地块自然键（`venue:slot_no`）+ 收获计数**（§23 落地约束）。

### 25.4 `garden_world`（第 11 张表，DDL 见 §16.4）一次解决三件事

1. **世界可寻址**：`world_id`（ULID）是存档 / 房间 / 结算票据 / 导入导出的统一标识；`id` 才是各表 `family_id` 列里的那个数。**两列分离**，让「外部标识」与「内部外键」各守其职。
2. **家庭级设置有了正确的家**：原设计把 `garden.time_ratio` / `garden.daily_points_cap` / `garden.tutorial_done` / `garden.achievements:{family_id}` / `garden.warned_date` 全存 `sys_parameter`。**实测该表无 `family_id` 列，且 `value` 只有 `VARCHAR(500)`**（ihomy 侧唯一先例是天气把 familyId 拼进 key 名）——22 条成就的 JSON 必然溢出。改存 `garden_world.settings`（MySQL 8 JSON，无长度上限）后：① 不再用「全局键值表」冒充家庭隔离；② **设置随存档走**，三端一致（互通性直接受益）；③ 世界级参数与全局参数的边界变清楚。
3. **血统与权威可追溯**：`host_epoch` / `imported_from` / `imported_at` / `settled_at` / `origin` 是 §29 迁移与结算的判定依据。

## 26. 单人模式（Solo）

### 26.1 定位与「明确砍掉什么」

| 做 | 不做（写清楚，避免实现期反复摇摆） |
|---|---|
| 全量核心玩法（十阶段 / 86 作物 / 变体 / 市集 / 食谱 / 专精 / 成就 / 晒图） | 兑换积分 |
| 本地多成员——**扮演全家**（专精与协作照常触发，§26.4） | 与真实家庭实时同步 |
| 可选匿名公开天气（`/api/public/weather` 免登录） | 依赖 ihomy 登录 |
| 存档导入 / 导出 / 迁移到 P2P 或服务器（§29） | 联机 |

### 26.2 本地后端：内存十张表 + 一个持久化适配器

- 把十张表实现为内存表（`Map<自然键, 行>`——天然对应 §25.1 的自然键），持久化到 **IndexedDB**（Web / PWA）或**单文件**（native 构建 `garden/<world_id>.save.json`）。
- **不把 SQL 塞进客户端**：只有 10 张表、规则全在纯函数里，用不上查询语言；引 SQLite(WASM) 会让包体与初始化成本翻倍。native 构建若确需 SQLite，**只换持久化适配器**，内存模型不变。
- **写入策略**：内存为真相 + 节流落盘（动作后 ≤1s / 页面隐藏 / 每 30s 兜底），落盘重试靠 `op_id` 去重。
- ⚠ **日志保留期在单人端同样生效**（§15.2 的 180 天 / 单家庭 5000 行上限），否则存档无限膨胀；且**删日志前必须先写 `garden_stat` 快照与 `garden_codex`**——顺序错了就是把等级与图鉴清零。

### 26.3 本地平台替身（能力降级表）

| 能力 | `IhomyPlatform` | `LocalPlatform`（Solo） | 依据 |
|---|---|---|---|
| 身份 | JWT claim `familyId` + `SecurityHelper` | `player_uid`（ULID，首次启动生成并存入存档） | — |
| 天气 | `WeatherService.getWeather(clientIp, familyLocation)` → `condition/temp/text/iconCode` | ① 匿名 `GET /api/public/weather`（**该端点免登录**）② 失败退回季节默认均温 | ihomy `/public/**` 在 `SecurityConfig` 白名单内 |
| 成员 | `sys_user_role` 成员列表 | 本地档案（§26.4） | — |
| 通知 | `NotificationService.create(...)` **逐成员调用** | 应用内 Toast / 桌面通知 | 该服务**无家庭广播、不排除本人**，须自己遍历 |
| 积分 | `PointsService.addRecord(...)`（需新 feature code，§30.4） | **关闭**（不渲染按钮） | §1 原则 10 |
| 冰箱 | `ItemService.itemCreate` + `getDefaultFridge` | 本地食材仓（同 `ingredient` 结构） | 该服务**无数量合并**，须自建按名 upsert |
| 照片 | `FileService.upload(...)` + `content_photo.visibility=FAMILY` | 本地文件 / 浏览器下载 | `/files/**` 对未登记文件 fail-closed |
| 注册表 | `game_info`（待改造，ihomy 侧事项） | 无 | §16.2 |

- ⚠ **天气是「可选增强」，不是依赖**：拿不到就按季节默认算（§17.1 已有「天气缺失不报错」口径），**不允许因为没网而无法开局**。

### 26.4 「扮演全家」：单人必须保住家庭玩法

> 单机版最容易被做废的地方：把家庭主题连同家庭机制一起砍掉，退回「一个人种地」。

- 单人世界允许建**多个本地成员档案**（昵称 + 头像 + 专精），随时切换操作 ⇒ **专精（§15.1）与协作加成照常触发**，「今日谁动过手」由本地档案的 `last_active_date` 推导。
- 三个好处：① 单机也符合「一圃藏四季，全家共耕耘」的主题；② §15.1 的五个专精与协作判定在**三端同一套**，社交规则不分叉；③ 玩家后来开联机时，**本地档案可直接认领成真实成员**（§29 / §30.3）。
- §15.1 的伦理约束照旧适用：无排名、无贡献对比——单机同样不做「谁干得多」的统计页。

### 26.5 离线结算与时间权威

| 项 | 规定 | 为什么 |
|---|---|---|
| 生长推进 | 按真实时间纯函数推进（`now - planted_at`） | 天然离线可玩，**不需要单独的「离线结算逻辑」** |
| 离线事件 | **不追溯**：离线期间不生成天气事件、不判霜冻、不发节气加成 | §22 已有边界（天气是采样不是历史），不能凭空补算 |
| 离线封顶 | `OFFLINE_SETTLE_CAP_DAYS = 30`，超出部分按 30 天算 | 防「关一年再开」式开局暴富；30 天 ≈ 4 游戏日（`REAL_TIME_SCALE`） |
| 时钟权威 | **本机时钟** | 单机改表是玩家自己的事；但导入服务器时全部时间戳要**净化**（§29.2） |
| 照料动作 | 离线不自动发生 | 加成只能「当时在场」拿到，离线收益本就弱于在线 |

### 26.6 入口与打包

- **同一份客户端构建产物**（Cocos web-mobile）：既作 ihomy 内的 `/tools/garden`（走 `HttpPort`），也作独立版（走 `SoloPort`）——不存在「单机版另一套客户端」。
- **模式由启动探测决定**（`/garden/meta`，§28.2）：探不到服务器 → Solo；`platform=IHOMY` → Server(ihomy)；`platform=STANDALONE` → Server(standalone)。
- 独立版入口：花园主场景 + `/worlds` 存档管理页（新建 / 导入 / 导出 / 认领，§29.4）。
- **Steam / 桌面**：同一个 Cocos **native 构建** + 本地文件持久化适配器（壳技术已定，§37.5）。**这不是另一套实现**——它是「一核三端」能否兑现的最后一个考验。

## 27. 多人 P2P 模式

### 27.1 拓扑：房主权威 + op-log 广播

> **为什么不选天真 lockstep（纯确定性重放）**：核心确实确定性（§1 原则 11），但天真 lockstep 把正确性押在「两端代码与 `content_version` 永远一致」上——玩家浏览器缓存一份旧 JS 就是状态分歧。**房主权威把真相源收敛成一个点，分歧不可能发生**；确定性只用来做两件事：客户端乐观预测 + §29.3 结算重放校验。

- **房主 = 单人模式 + 一个房间服务**（op 串行执行器 + 广播），**代码复用率接近 100%**。这是把 §26 与 §27 写在一起的理由：P2P 不是新引擎，是单机后端加一层网络。
- **成员**只发意图、收结果；本地用同一核心做**乐观预测**让界面即时响应，收到结果后以房主为准回滚差异。

### 27.2 协议只有三条消息

| 消息 | 方向 | 内容 | 用途 |
|---|---|---|---|
| `garden.op` | 成员 → 房主 | `{op_id, lamport, actor_uid, plot_key, action, payload, client_ts}` | 提交意图（`action` 枚举与 §15 同源） |
| `garden.patch` | 房主 → 全员 | `{op_id, accepted, rev, changed:[{table,key,row}], reason}` | 执行结果（拒绝原因复用 §17.1 错误码语义） |
| `garden.snapshot` | 房主 → 新加入者 | `GardenSave` 全量（头 + payload） | 加入时一次拉齐 |

- ⚠ **只广播变化，不广播全量状态**：36 块地 × 成员数的全量包在弱网下会让操作延迟肉眼可见；`changed` 通常 1~3 行。
- ⚠ **`plot_key` 用自然键**（`venue:slot_no`），不用自增 `id`——两端自增 id 必然不同，只有自然键能对齐（§25.1）。
- ⚠ **`client_ts` 只用于界面展示**（「小明 2 分钟前浇水」），**不参与任何判定**（防改时钟）。

### 27.3 冲突与并发：房主串行化，判定逻辑与服务器同源

- 房主收到 op 后**单线程串行执行**：先跑 `garden-core` 的 guard（「冷却中？未成熟？园币够？」），通过则改状态并广播 patch；不通过回 `accepted=false` + 原因码。
- **这与服务器 §17.1「条件 UPDATE + 0 行即失败」是同一件事的两种实现**：服务器用 SQL 条件更新，房主用内存条件判定，单人直接执行——**三端只有一份 guard 代码**。所以「同一动作在三种模式下的合法性完全一致」，这就是「数据可互通」在机制层的兑现方式。
- 极端情况（两人同时收获同一块地）由**房主的串行队列天然解决**：第二个 op 的 guard 判定「地块已空」直接拒绝。**不需要 CRDT、不需要向量时钟**——这是选房主权威换来的最大简化。
- 唯一看似要「计数合并」的仓库（多人同时入库）同样因串行而退化为普通累加，**也不需要 CRDT**。

### 27.4 离线成员与重连：只交意图，不交状态

- 成员可离线做本地预测，重连时**只重放未确认的 op**（按 `op_id` 去重），**绝不上传状态**——上传状态等于上传一个可任意伪造的真相；只交意图则会被房主的 guard 归一成「一个合法动作」。
- ⚠ 离线操作**在房主收到的那一刻执行**：离线 3 天的浇水 = 「重连那一刻浇的水」，冷却从那一刻起算，**不追溯**（同 §22 边界）。UI 重连时提示「有 N 个离线操作已按当前时间执行」。

### 27.5 房主接管（防「房主一关就散伙」）

- 每个成员本地保留**op-log 尾段 + 周期快照**（默认每 5 分钟或每 50 个 op 落一次）。
- 房主离线超过 `HOST_TAKEOVER_MINUTES = 10` ⇒ 任一成员可发起接管：以自己持有的**最新 op 序号**为准，`host_epoch + 1`，广播 `garden.snapshot` 重建房间。
- ⚠ **旧房主的 op（`host_epoch` 落后）一律拒绝**——防「两个房主同时活着」造成分叉，这是 P2P 最容易出的致命 bug。
- **可选云备份**：房主可把存档只读快照上传 ihomy（`FAMILY` 可见）用于设备丢失；**备份不参与权威**，取回要走 §29 导入流程。

### 27.6 连接与信令：三级，且「只转发不落库」

| 级 | 场景 | 实现 | 服务器角色 |
|---|---|---|---|
| **L1** 局域网 / 同机 | 同 Wi-Fi、面对面 | 手动交换**连接码**（含 SDP/ICE 的短串或二维码）→ 直连 | **零服务器** |
| **L2** 借道 ihomy 信令 | 异地亲友（双方均已登录 ihomy） | 新增 `/garden/rtc/signal`（WebSocket）转发 SDP/ICE | **只转发**：不落库、不进 `garden_log`、不记正文 |
| **L3** 兜底中继 | NAT 穿透失败 | 公共 STUN + TURN 中继 DataChannel | 载荷已被 DTLS 端到端加密，服务器读不到 |

- ⚠ 信令鉴权用短时 `room_ticket`（§28.3 签发）或 L1 的一次性连接码；**房间内的游戏数据不经服务器**（除 L3 的加密中继）——隐私口径：花园内容默认只在玩家设备之间流动。
- ⚠ L1 是**必须有的降级路径**：服务器不可用时，同 Wi-Fi 的两个人仍要能联机。否则「P2P」实际上又变成了「必须有服务器」。

### 27.7 P2P 的玩法（`kind=COOP`）

> P2P 不是「家庭模式的局域网版」，而是**邻里 / 亲友玩法**：互相看得见、能帮忙、能送东西，但不能互相算计。

| 玩法 | 规则 | 为什么这么设计 |
|---|---|---|
| **串门** | 可只读查看房间内其他成员的世界投影 | 零新表、强社交 |
| **互赠** | `GIFT`：把自己仓库的物品移给对方（不可逆、无价签） | **只做赠送，不做跨世界定价交易**——跨世界市集会让人跨世界套利，直接违反 §12.1 币种隔离 |
| **共建地** | 世界可加一小片 `kind=COOP` 公共地（无主），任何人可照料、产出进公共仓库 | 复用 §15.1 的协作判定，**零新机制** |
| **专精 / 协作** | **原样沿用 §15.1** | 三端同一套判定，社交规则不分叉 |
| **伦理约束** | 无排行、无贡献榜、不显示「谁给得多」 | §15.1 是产品底线，P2P 不例外 |
| **不做** | 无积分、无跨世界交易、无 PvP、无排名 | §1 原则 10 |

### 27.8 反作弊：说实话，而不是假装

- 房主**在技术上不可信**（房主可以改存档）。本设计**不假装 P2P 是安全的**，而是**把不可信性隔离在玩法层**：P2P 不发积分、不给跨模块出口、不参与任何全局排名。
- 唯一通往可信的路径是 §29.3 的 **op-log 结算网关**——它校验的是**操作序列**而不是「声称的状态」。这是让 P2P 玩家拿到积分的唯一诚实做法。

## 28. 服务器模式（同协议，两个 provider）

### 28.1 同一协议，两个 provider

> 「连接 ihomy 服务器即可与 ihomy 互联互通」的落实方式：**同一条 `/api/garden` 协议 + `meta` 里的一个 `platform` 字段**。客户端不写两套逻辑，只按能力开关显示。

| | `platform=IHOMY` | `platform=STANDALONE` |
|---|---|---|
| 宿主 | ihomy 服务（Java 21 / Spring Boot 3.5 / MyBatis-Plus 3.5.5 / MySQL 8 / Redis 8） | 独立部署的 garden 服务（**同栈**，§28.5） |
| 世界来源 | ihomy 家庭（`sys_family_info.id`）；`garden_world.id = family_id`（恒等映射），`external_ref='ihomy:family:<id>'` | 自建世界（`garden_world.id` 自增，与 ihomy 家庭无关） |
| 身份 | ihomy JWT（claim `familyId`）+ `SecurityHelper` | standalone 令牌（可先匿名建世界，登录后绑定） |
| 积分 | ✅ `PointsService` + `PointsRuleService` | ❌ |
| 冰箱 | ✅ `family_item` | 自建食材仓 |
| 天气 | ✅ `WeatherService`（家庭坐标 `sys_family_info.weather_lat/lng/city`） | 公开天气源或季节默认 |
| 通知 | ✅ `NotificationService`（逐成员） | 站内通知 |
| 照片 | ✅ `FileService` + `content_photo` | 自建 / 无 |
| 注册表 | ✅ `game_info` + `sys_home_module` | 无 |
| 表 | **`games` 库的 11 张 `garden_*`**（不动 ihomy 的 81 张） | 独立库，**同样的 11 张** |

- ⚠ **两个 provider 的表结构完全相同**：「连 ihomy」与「连自有服务器」的差别**只在 platform 适配层**，不在数据模型。这是「数据可互通」的第二条兑现路径——**同一份存档既能喂 ihomy，也能喂 standalone**。

### 28.2 能力协商：`GET /garden/meta`（新增端点，三端统一入口）

```json
{ "protocol_version": "1.0", "platform": "IHOMY", "content_version": "<sha256>",
  "capabilities": { "points": true, "fridge": true, "weather": true, "notify": true,
                    "photo": true, "registry": true, "realtime": "WS", "p2pSignal": true },
  "world": { "world_id": "01J...", "kind": "FAMILY", "origin": "IHOMY", "authority": "SERVER" } }
```

- 前端按 `capabilities` 渲染：`points=false` ⇒ 兑换入口**不出现**（不是置灰——不存在的功能不该露出）；`realtime=WS` ⇒ 用推送替代 §18 的 30s 轮询。
- ⚠ **协议版本不匹配**：只读模式 + 提示升级，**不做静默降级**。
- 三端各自给出等价 `meta`：Solo 由本地静态文件（`platform=LOCAL`），P2P 由房主（`platform=HOST`）。

### 28.3 世界票据（`world_ticket`）与实时推送

- **票据**：服务器签发短时票据，用于 ① P2P 房间鉴权（§27.6 L2）② 世界认领（§29.1）③ op-log 结算（§29.3）。票据携带 `world_id` / `content_version` / `exp`，**不携带游戏数据**。
- **实时推送**：ihomy 已有原生 WebSocket（`/ws/chat`，握手自校验 JWT），新增 `/ws/garden` 同构，替代 30s 轮询；standalone 同样实现。
- ⚠ 推送是**优化不是依赖**：断线仍靠重连补全，因为全部权威判定都在服务端（§17.1）。

### 28.4 服务器模式独有的玩法

| 玩法 | 说明 | 为什么只有服务器能做 |
|---|---|---|
| **全服节气** | 同一服务器所有世界共享节气日历 ⇒ 可做「全服共庆」（今日全服流星雨，所有家庭同享 buff） | 需要共同时钟与统一真相源 |
| **家庭周挑战** | §15 复用 `family_task` | 需要跨成员聚合 |
| **积分与冰箱出口** | §12 单向兑换 + 入厨 | ihomy 生态 |
| **官方市集保底价** | §12.2 系统保底 | 需要可信定价源 |

### 28.5 standalone provider 的定位与「不做什么」

- **定位**：① 不想用 ihomy 的玩家 / 社群的自建服务器；② 未来商业发行（Steam 联机档）；③ **「数据可互通」的中立验证器**——只有它能证明存档不依赖 ihomy 的任何表。
- **共用同栈**（Java 21 + Spring Boot + MySQL + Redis）：`garden-core` 作为**无依赖纯函数模块**（jar）被两个 provider 引用，避免「另一套实现」的漂移。⚠ 这是**对技术栈待定的一次强约束**：核心必须能被如此抽出（§21 技术栈定型时的判据）。
- **不做**：不引服务发现 / 微服务 / 消息队列 / 多租户改造。世界数少、并发低（§22 判断口径不变），**单体 + 一个库**足够；standalone 是**部署形态**，不是新架构。

## 29. 模式迁移、权威与结算（「互通」的执行条款）

### 29.1 迁移矩阵：互通的是「世界」，不是「任意状态」

> 诉求是「保证数据可互通」。**必须同时给出边界**，否则「可互通」就等于「可任意回灌」——单人改存档 → 导入家庭 → 兑换积分，§12 的经济会在一天内被刷爆。所以口径是：**世界与存档可移动；移动后的存档按来源享有不同信任级别。**

| 迁移 | 允许 | 规则 |
|---|---|---|
| S → S（换设备 / 备份） | ✅ | 导出 / 导入 `*.garden.json`；`content_version` 相同即可直接用 |
| **S → C（新世界）** | ✅ | 「**认领**」：`world_id` 未被占用即可建新世界；`origin` 记 `LOCAL`、落 `imported_at`；**全部时间戳净化**（§29.2） |
| S → C（已有世界） | ❌ | 禁止回灌。已有世界只接受 `garden.op`（动作），不接受状态 |
| **P → C** | ⚠ | 只经 **op-log 结算网关**（§29.3）；不接受状态上传 |
| **C → S** | ✅ | 导出为**可玩副本**（`origin=SERVER_SNAPSHOT`、`authority=LOCAL`）；副本**不可再回灌**任何服务器世界 |
| C → P | ⚠ | 房主用服务器签发的 `world_ticket` 开房（`host_epoch` 从服务器值起步），成员凭票据加入 ⇒ 房间与服务器世界**同源**，op-log 可直接结算 |
| 跨服务器（ihomy ↔ standalone） | ✅ | 走 `*.garden.json` 导入（= S → C 路径） |

**三条玩家旅程**（把矩阵翻译成人话，同时是验收用例）

1. **一个人先玩，后来全家一起**：Solo 建世界 → 玩到中期 → 导出存档 → 在 ihomy「认领」为家庭世界 → 邀请家人 → **本地档案认领成真实成员**（§30.3）。园币 / 图鉴 / 进度全保留。
2. **亲友串门**：家庭世界 → 房主凭 `world_ticket` 开 P2P 房间 → 非家庭亲友加入为 `COOP` 成员 → 关房后世界仍是原家庭世界（权威回 `SERVER`）。
3. **离线续玩**：家庭世界 → 导出可玩副本 → 飞机上单人玩 → 回来**不合并**（副本是副本）。**明确拒绝合并**是有意为之：合并两份都权威过的状态需要 CRDT 与仲裁，收益远小于成本与 bug 面。

### 29.2 导入时的数据净化（不净化就等于开后门）

| 项 | 处理 | 为什么 |
|---|---|---|
| 时间戳 | 全部 `*_at` **钳制到 ≤ `imported_at`** | 防「把系统时钟改到 2099 → 全部成熟 → 收获 → 导入」 |
| 离线封顶 | 按 `OFFLINE_SETTLE_CAP_DAYS` 折算 | 同 §26.5 |
| `player_uid` | 保留；无 `sys_user_id` 的成员标为「未绑定」，由邀请人**逐个认领** | 不把本地档案自动当成真实用户 |
| `world_id` | 已存在 ⇒ 拒绝并提示「另存为新世界」 | 防覆盖 |
| `family_id` 列 | 全部改写为**新分配的 `garden_world.id`**（从 `WORLD_SCOPE_ID_IMPORT_BASE` 起，避开 ihomy 家庭号段） | 作用域换装（§25.2） |
| `garden_log` | 按 `op_id` 去重后插入；`SETTLE` 类 op 不可导入 | 重复导入不翻倍 |
| `garden_buff` / `garden_listing` | 按 `expire_at` 过滤（过期即丢），其余重分配主键 | 暂态，跨端重放无意义 |
| 图鉴 / 快照 / 成就 | 保留 | 收集成果不该丢 |
| `origin` | 落 `LOCAL` / `SERVER_SNAPSHOT`，**不可篡改** | §29.3 与 §12 积分闸门的判定依据 |

### 29.3 op-log 结算网关（P2P → 积分的唯一诚实路径）

- **输入**：`world_ticket` + `content_version` + 一段 `garden.op` 序列（带房主序号 / 签名）。
- **服务器动作**：用**同一份 `garden-core`** 在服务端**重放**这些 op，逐步执行 guard；通过的落成权威状态并产出园币 / 图鉴 / 积分，不通过的丢弃并回执原因。
- **为什么这样能信**：服务器校验的是**操作合法性**（「这次收获时，作物按服务器时间戳算确实成熟了吗」），不是玩家声称的状态。**改存档没有意义，因为存档不参与结算。**
- **时间口径**：结算时时间戳由**服务端重新盖**，所以「P2P 里改时钟」在结算这一步归零。
- ⚠ **分期**：结算网关**不进 P1–P5**（它是 P2P 的增值项，不是主线）。落地前的口径是 **P2P 无积分**，UI 明示——这样「互通」与「经济安全」解耦，不必为 P2P 拖慢主线。
- ⚠ **候选，未排期**（与 §21 的「年度回顾」同列）；若落地，它同时是「P2P 世界的可信云存档」入口。

### 29.4 存档管理 UI（`/worlds`）

- 世界列表：世界名 / `kind` / `origin` / 权威 / 最后游玩 / `content_version` 是否兼容。
- 动作：新建 / 导入（`*.garden.json`）/ 导出 / 认领到家庭 / 删除。
- ⚠ **跨 `content_version` 导入必须给出差异清单**（「存档含 3 种已删除作物：xx / yy / zz」），**不静默丢数据**。
- ⚠ **世界级删除口径待定**：本地世界是物理删；服务器世界的删除走软删 + 回收站还是物理删，**验收前必须定**（§16.4 要点 4 的「不需要软删」针对的是地块 / 仓库这类游戏数据，世界级删除是另一回事）。

### 30.3 身份与世界绑定（`player_uid` ↔ `sys_user_id`）

- **判定规则**：`garden_member.sys_user_id` 有值 ⇒ 该成员可走 ihomy 出口（积分 / 冰箱 / 通知 / 照片）；为空 ⇒ 本地档案或未绑定访客，**只能用世界内能力**。
- **自动绑定**（ihomy 模式）：登录用户首次进花园即建 `garden_member` 行并写 `sys_user_id`。
- **认领绑定**（导入场景）：邀请人逐个把本地档案的 `sys_user_id` 填上（§29.2）。
- ⚠ **不新建用户体系**：花园不创建 ihomy 用户、不代发登录态。`player_uid` 是花园内部标识，`sys_user_id` 是外部引用，**单向绑定、永不互相覆盖**。

### 30.4 接入积分的三个前置动作（缺一个都被卡）

1. **新增 feature code**：在 `PointsRuleConst.FEATURES` 加（如 `garden_harvest`），否则 `PointsRuleService.effective` 视为关闭、拿不到分。⚠ 与 V1 的 `plant_water / plant_sun / plant_harvest` 的**并存或替代关系必须定**（建议 V2 用新码，V1 的码随 `family_plant` 一起下线）。
2. **带对 `familyId`**：流水行的 `family_id` 要填对（余额虽按 `user_id` 求和，但归属与商城隔离用它）。
3. **家庭级开关**：家长可关花园加分（§12.4 口径）＝ `family_points_rule` 该 code 的开关行，**不新造开关表**。

### 30.5 边界与禁止事项

- ⚠ **不写 ihomy 的表**（除 §16.2 标注的 `game_info` 注册表改造，且那是 **ihomy 仓事项**）——花园只**调用** ihomy 服务接口。
- ⚠ **不改 `sys_parameter` 的全局值**：花园自己的家庭级设置进 `garden_world.settings`。
- ⚠ **不给 ihomy 新增权限码**（沿用「登录即可 + 家庭隔离」）。
- ⚠ **不把 ihomy JWT 复制到非 ihomy 端**：P2P 成员各持自己的登录态，信令端点只认票据。
- ⚠ **反向路径不存在**：`积分 → 园币` 不通（§12.1）；`服务器世界 ← 状态回灌` 不通（§29.1）。

## 31. Steam 上架与跨平台方案

### 31.1 核心决策一：一核三端扩展为一核三端四平台

当前设计稿的「一核三端」指三种运行模式（Solo / P2P / Server），Steam 上架要求扩展为四种平台（Browser / Desktop / Mobile / Console），核心仍是同一份 `garden-core` 纯函数，只是边界层不同。

| 平台 | 权威 | 存档 | 技术壳 | 说明 |
|---|---|---|---|---|
| **Browser** | Solo / 房主 | IndexedDB / 文件 | **Cocos Creator 3.8** 的 web-mobile 构建 + Rust 核心（WASM） | 浏览器 / ihomy 内嵌，支持跨设备同步 |
| **Desktop** | Solo / 房主 | 文件 | **Cocos Creator 3.8** 的 native 构建 + Rust 核心 | Steam / PC 桌面 |
| **Mobile** | Solo / 房主 | 文件 | **Cocos Creator 3.8** 的 native 构建（iOS / Android） | 家庭手机端 |
| **Console**（未排期） | Server | 服务器 | 需另定（引擎能否上主机视厂商授权） | 未排期 |

**核心原则**：
- **核心不变**：`garden-core` 不依赖平台，只通过 `GardenPort` / `GardenPlatform` 适配
- **存档统一**：`GardenSave v2`（Steam Cloud 友好格式）跨平台通用
- **身份统一**：`player_uid` ↔ `steam_id` 双向绑定，跨设备识别

### 31.2 核心决策二：Steam Cloud 统一存档

Steam Cloud 是跨设备同步的核心基础设施，`GardenSave v2` 必须支持 Steam Cloud 自动上传/下载。

**存档路径**：
- **Steam Cloud**：`%LOCALAPPDATA%\Steam\userdata\<steam_id>\<app_id>\remote\garden_save.json`
- **本地备份**：`~/Documents/GardenMoments/backups/garden_save_<timestamp>.json`

**同步流程**：
1. **首次启动**：读取本地存档 → 上传到 Steam Cloud
2. **云端有新版本**：下载覆盖本地（以最新 `last_synced` 为准）
3. **本地有新版本**：上传覆盖云端（冲突解决：以最新 `last_synced` 为准）
4. **断线处理**：本地缓存最新版本，待网络恢复后同步

**冲突解决规则**：
- **同设备多端**：以最新修改时间为准（覆盖旧版本）
- **跨设备冲突**：以最新 `last_synced` 为准（覆盖旧版本），并在 UI 提示「版本冲突，已自动合并」

### 31.3 核心决策三：Steamworks SDK 集成点

Steam 上架必须集成以下 Steamworks 功能：

| 功能 | 优先级 | 说明 |
|---|---|---|
| **Steam Guard 短信验证** | P1 | 绑定手机号，验证玩家身份 |
| **玩家资料（Steam ID）** | P1 | `player_uid` ↔ `steam_id` 双向绑定 |
| **成就系统** | P1 | Steamworks Achievement API，家庭通知联动 |
| **反作弊** | P1 | Steamworks Anti-Cheat，防篡改存档 |
| **多语言支持** | P2 | Steam 多语言文件（`lang/<lang>/*.json`） |
| **Steam Overlay** | P2 | 游戏内截图 / 暂停 / 调试工具 |

### 31.4 核心决策四：Steam Deck 支持

Steam Deck 要求游戏在 Linux 上也能运行，同时保持 60fps。

**Linux 支持检查清单**：
- [ ] Rust 核心编译为 Linux 二进制
- [ ] 客户端用 Cocos 的 **Linux native 构建**（Steam Deck）
- [ ] ⚠ Rust 核心在 native 构建里的绑定方式（原稿的 `napi` 不适用，见 §32.2）
- [ ] 触摸屏适配（§6.1 的地块网格需支持触摸手势）
- [ ] 性能优化（36 块地渲染 + 多人同步）

**触摸屏适配**：
- 地块网格支持点击/长按/滑动手势
- 长按地块显示快捷操作菜单（浇水/施肥/收获）
- 滑动切换场域（类似 App 的横向滑动）

**性能优化**：
- 渲染层面：只渲染可见地块 + 延迟加载（按场域分批加载）
- 逻辑层面：多人同步用 op-log 批量处理，避免实时计算
- 资源层面：纹理压缩 + 图集 + 分包（见 `CocosCreator资源管理规范.md` §2.4）

## 32. 核心层技术栈（Rust/WASM）

### 32.1 方案对比

| 方案 | 优势 | 劣势 | 推荐度 |
|---|---|---|---|
| **Rust + WASM** | 性能好、内存安全、跨平台、单一代码库 | 开发工具链较重 | ⭐⭐⭐⭐⭐ |
| **TypeScript + WebAssembly** | 开发工具链成熟、学习成本低 | 性能略逊、GC 压力 | ⭐⭐⭐ |
| **Rust + 原生二进制** | 性能最优、无 WASM 限制 | 需要为每个平台编译 | ⭐⭐⭐⭐ |
| **双路径** | 兼顾浏览器与原生 | 开发成本高 | ⭐⭐⭐⭐ |

### 32.2 最终决策：Rust 核心（Web 绑定 `wasm-bindgen`；原生绑定待重定）

**决策依据**：

1. **核心确定性是三端重放一致的前提**（§1 原则 11）
   - Rust 的内存安全避免竞态条件
   - 纯函数核心无副作用，易于测试

2. **跨平台需求**（§31.1）
   - 浏览器：需要 WASM
   - 桌面：需要原生绑定
   - 移动：需要原生绑定
   - **单一代码库，两种绑定，开发成本最低**

3. **性能要求**（§35.3）
   - 36 块地 + 多人同步 + 实时天气
   - Rust 比 TypeScript 快 2–5 倍（无 GC 压力）
   - WASM 比 TypeScript 快 1.5–2 倍（无 JS GC）

4. **维护成本**（开发成本）
   - Rust 核心：单一代码库；Web 绑定 `wasm-bindgen` 已定，**原生绑定待重定**（原稿写「两种绑定 wasm-bindgen / napi」，其中 `napi` 的宿主是 Node/Tauri，改 Cocos 后不适用）
   - Rust + 原生二进制：需要为 Windows / macOS / Linux 编译三个二进制
   - 双路径：需要维护两套绑定（WASM + 原生）

5. **工具链成熟度**
   - wasm-bindgen：浏览器绑定工具，成熟稳定
   - 原生绑定：⚠ **待重定**。原稿写 `napi`（Rust → C++ → TS），它的宿主是 Node.js / Tauri；客户端改 Cocos 后，native 构建的 JS 跑在 Cocos 自己的 JS VM 里，**`napi` 不是这条路**，需改为「Rust 静态库 + Cocos 自定义原生绑定」或另选方案（`garden-native` 现状需复核）
   - cargo：Rust 包管理器，依赖解析完善

**最终方案**：**Rust 单一代码库**；Web 端绑定 `wasm-bindgen` 已定，**原生端绑定方式待重定**（不再预设 `napi`）。

### 32.5 `GardenCore` API 接口设计

**核心原则**（§1 原则 11）：
- **纯函数**：所有函数无副作用，不修改状态，只返回结果
- **确定性**：禁 `Math.random`、禁直接取 `now()`、禁浮点比较（一律整数基点）
- **依赖注入**：时间、天气、随机源由调用方注入

```rust
    }
```

### 34.4 反作弊与防作弊

```rust
pub struct AntiCheat {
    api: SteamAPI,
}

impl AntiCheat {
    pub fn init(&self) {
        self.api.set_anti_cheat_enabled(true);
        self.api.set_timeout_disconnect(true);
    }

    pub fn validate_save(&self, content: &str) -> Result<(), String> {
        // 校验文件签名
        let signature = self.api.sign_save(content)?;
        let stored_signature = self.get_stored_signature()?;

        }
        Ok(())
    }
}
```

### 35.3 性能优化

**渲染层面**：
- 只渲染可见地块 + 延迟加载（按场域分批加载）
- 使用对象池 + 按场域分批加载地块卡（Cocos 里没有 DOM 虚拟滚动这回事，靠实例复用与分包解决）

**逻辑层面**：
- 多人同步用 op-log 批量处理，避免实时计算
- 天气与营养计算按需触发，不每帧计算

**资源层面**：
- 纹理压缩 + 图集 + 分包（见 `CocosCreator资源管理规范.md` §2.4）
- 减少包体，加快加载速度

## 37. 游戏引擎选择与架构（Cocos Creator 3.8 + Rust 核心）

> **2026-10-13 改写**：本节原稿的结论是「不需要游戏引擎 / 纯 Web + Tauri」，**该结论已作废**。客户端定为 **Cocos Creator 3.8**，理由是它一套代码同时覆盖 Web（web-mobile 构建，可嵌 ihomy）与桌面/主机（native 构建，Steam 上架），且渲染、动画、图集、分包、对象池、音频、截图这些原稿要在 §18.1 里自己糊的东西引擎自带。代价是引入引擎依赖与一整套资源/构建体系（见 `CocosCreator资源管理规范.md`）。

### 37.1 核心决策：采用游戏引擎，客户端统一为 Cocos Creator 3.8

**为什么改**（对原稿「不需要引擎」三条理由逐条回应）：

| 原稿理由 | 现状 |
|---|---|
| 游戏主体是网格布局，不是复杂 3D 场景 | 仍成立，但**不等于不需要引擎**：动画、图集、分包、触摸手势、音频、截图、Steam 原生构建都得有人做 |
| SVG + CSS 渲染，纯 DOM 操作性能足够 | **前提消失了**：Cocos 的画面不在 DOM 里，SVG/CSS 这套直接不适用 |
| 动画用 CSS transition + rAF，不需要引擎动画系统 | 同上；换引擎后动画走 Cocos 的 `Tween` / `Animation` |

**保留不变的三条设计约束**（与引擎无关）：
- **三层渲染契约**：作物视图组件的公开接口稳定，内部实现可换（§18.1）
- **极简参数化资产**：形状 × 参数组装，不画 86×6 张图（§18.1）
- **风格约束**：无渐变 / 统一描边 / 统一投影 / 跟随主题色板（§18.1）

### 37.2 技术栈选择对比

| 方案 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **Cocos Creator 3.8**（**已采用**） | 一套代码出 Web / Windows / macOS / Linux / iOS / Android；渲染、动画、图集、分包、对象池、音频、截图齐全；**native 构建可直接上 Steam**；2D 扁平风格是它的主场 | 引入引擎依赖与一套新的资源/构建体系；需装编辑器（多一条 TS 之外的工作流） | ⭐⭐⭐⭐⭐ |
| **Phaser 3** | 轻量 2D 引擎、社区大 | 无原生构建（Steam 需另套壳）；UI 与资源体系要自己搭 | ⭐⭐⭐ |
| **Unity / Godot** | 功能最强大、生态最成熟 | 体积大、2D 扁平场景过度设计、与 ihomy 的 Web 内嵌集成更重 | ⭐⭐ |
| **纯 Web + SVG/CSS**（原稿方案，已弃） | 零引擎依赖 | 换引擎后前提消失；Steam 原生构建无解 | — |

**采用方案**：**Cocos Creator 3.8（客户端）+ Rust `garden-core`（核心）**

### 37.4 渲染层实现

**作物视图组件**（§18.1 的 10 种形态；公开接口就是三层契约里那一层）：
```ts
// CropView.ts —— 挂在作物节点上，公开接口稳定（§18.1 三层契约）
@ccclass('CropView')
export class CropView extends Component {
    @property
    cropCode = '';
    @property
    stage = 1;
    @property
    variant = '';        // 变体短码（如 D-MAG-PINK），空串表示无变体
    @property
    wilted = false;

    private _form: CropForm = 'ERECT';  // ERECT/CLIMB/MAT/CRAWL/FLOAT/TRAP/HANGING/ROSETTE/BUSH/TREE

    /** 参数来自 content/crops.json 的 sprite_param；阶段差异在这里插值，不逐阶段出图 */
    apply(cropCode: string, stage: number, variant: string): void {
        const param = ContentStore.getSpriteParam(cropCode);
        this._form = param.form;
        const s = param.scaleAt(stage);
        this.node.setScale(s, s, 1);
        this.applyVariant(variant);
    }

    /** 变体：叶纹叠通用遮罩贴图，花色走 Sprite 颜色 tint（§18.1 资源清单） */
    private applyVariant(variant: string): void {
        if (variant.length === 0) { return; }
        void ResourceManager.instance.loadSpriteFrame(cropVariantOverlayPath(variant));
    }
}
```

**动画实现**（Cocos `Tween`；粒子走对象池，不每次 `instantiate`）：
```ts
// 浇水：水珠从壶口落向地块
tween(waterDropNode)
    .to(0.5, { position: new Vec3(0, -50, 0), scale: new Vec3(0.4, 0.4, 1) }, { easing: 'quadOut' })
    .call(() => { waterDropNode.active = false; })
    .start();

// 施肥粒子：从对象池取，用完还回去（§3 性能基线）
const p = this._fertilizerPool.get();
tween(p)
    .to(0.6, { position: new Vec3(10, -30, 0), scale: new Vec3(0, 0, 1) }, { easing: 'quadOut' })
    .call(() => { this._fertilizerPool.put(p); })
    .start();
```

### 37.5 native 构建（Steam / 桌面）

Cocos Creator 3.8 的构建目标在**构建面板**里选，**不需要额外的桌面壳**（原稿的 Tauri 壳在这一节作废）：

| 目标 | 构建模板 | 产物 | 用途 |
|---|---|---|---|
| Web Mobile | web-mobile | JS + WASM + 资源 | 浏览器 / ihomy 内嵌 |
| Windows | native | exe + dll | Steam（Windows） |
| macOS | native | .app | Steam（macOS） |
| Linux | native | 可执行文件 | Steam Deck / Linux |

**平台检测要在客户端侧、按运行期判断**：

```ts
import { sys } from 'cc';

// ⚠ 原稿的 cfg!(target_os) 是 Rust 的编译期判断，识别的是「核心被编成了哪个目标」，
```

### 37.7 未来扩展性

**如果未来要加 3D 效果**：
- 当前设计稿是**扁平化 2D**，3D 效果可能影响 Steam Deck 流畅度
- Cocos 本身具备 3D 能力，**不需要换引擎**；可在 P5 之后按需打开，但优先保持 2D 扁平风格

**如果未来要加复杂动画**：
- 优先用引擎自带的 `Animation` / `Tween` / 时间轴，粒子用引擎粒子系统
- GSAP 与 Cocos 的节点体系不是一套东西（GSAP 操作 DOM），**不再作为 Cocos 客户端的动画方案**
